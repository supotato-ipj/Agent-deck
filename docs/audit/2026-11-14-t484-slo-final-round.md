## 一、测量方法（ADR-0032 口径兑现）

- **对象与口径**：面板**进程组**（electron 主进程整棵子进程树，含 GPU/renderer/utility 子进程，
  10 pid 左右）`TotalProcessorTime` 差分 ÷（墙钟 × 16 逻辑核）×100 = 整机百分比——与任务管理器
  进程页整机口径同向。工具 = #475 入仓的 `app/scripts/panel-cpu-sample.mjs`（起止两拍按集合交集
  记账，churn 单列）。
- **编排**：guard `hold --as zcode --purpose accept-sprint` 托管，每轮 guard 自动清场（含生产面板）
  → 编排器拉起工作树构建的面板（`--panel` + `DECK_RESIDENT_EVENT_LOG` 隔离落点 +
  `DECK_CDP_PORT`）→ 三线逐项测量 → `--panel-quit` 信使优雅退 → 收尾恢复生产面板（主检出
  `--panel` 链，窗口级判据核验在场）。
- **轮次**：
  - **hold 1（19:51–20:07，出证轮）**：冷启动 r1 + 点击 r1（探针初版，见 deviations ①②）+
    Win+D shell 态探针 + 冷启动 r2/r3 + **空闲 CPU 12 分钟长测**（30s 静置 + 720s 采样，
    背景负载 10s 拍全程标注）。
  - **hold 2（20:13–20:15，出证轮）**：点击 r2（修正后的四通道并行轮询编排器）+ Win+D 复探 +
    冷启动 r4 + 布局还原核对 + 生产面板恢复。
  - **hold 3（20:15–20:23，归因探针轮）**：面板逐 pid CPU 分账（60s）+ 对照组 A/B（§四）。
- **环境标注（#478 教训：环境因子可大于形态差异，必须同窗量化）**：hold 1 的 `envProbe` 三拍
  （pre/cpu-pre/cpu-post）+ 10 秒拍背景负载序列（`machine-load.jsonl`，覆盖 CPU 采样窗的后段
  41/70 拍）。**采样窗机器总负载均值 ~11%（中位 9%）**——本机 zcode 常驻会话、msedge、WmiPrvSE
  等在跑，不是静默夜窗；面板组读数按差分法不受背景负载直接污染（它量的是面板自己的 CPU 时间），
  但调度争用语境如实在此留痕。shell 态：Progman 在场、**Win+D 全天失效维持**（#475 留痕同状态，
  本轮两探针复测均 minimized=false，见 §五）。

## 四、线①余量归因：逐 pid 分账 + 结构对照（重写重议门槛的反证材料）

### 逐 pid 分账（60s 静置窗，`t484-samples/perpid-60s.json`）

| 进程 | 形态标签 | 整机 % | 说明 |
|---|---|---|---|

| main（pid 13688） | 主进程 | **0.438%** | 内核服务装配 + 任务栏控制器 + win-event 泵 + 桌面守望兜底拍 |

| 其余（renderer/utility/bridge.exe） | — | ≤0.003% | — |
| **组合计** | | **1.322%** | （60s 短窗，与 720s 长测 1.251% 同量级 ±0.1pp） |

### 结构对照（对照组 A/B，`control-bare.json` / `control-transp.json`）

| 对照 | 形态 | 整机 %（组口径，30s 静置 + 120s 采样） |
|---|---|---|
| A：control-bare | 同版本 Electron（44.4.3）零窗常驻 | **0.010%** |
| B：control-transp | A + 全屏透明置顶窗（面板同款 frameless+transparent+fullscreen 结构 + 1s 心跳） | **0.189%** |

### 归因结论（诚实版）

1. **框架结构性地板实测 ~0.19pp**（引擎空转 0.01 + 全屏透明窗合成在进程组内的份额 ~0.18），
   仅占面板组 1.25% 的 **~15%**。ADR-0032 预判的结构地板（1.5~3%）实测显著更乐观——Electron
   + 全屏透明窗本身近乎免费。
2. **余量主体（~1.1pp）是我方业务进程**：数据面 utility 0.805% + 主进程 0.438%（含其引擎底噪
   ~0.01 以下）。即：**>1% 目标线的缺口 0.25pp 完全落在业务侧**，压进 1% 的路径是我方代码
   （数据面再降频/事件化的余地），不是换框架。
3. **重写重议门槛两条均不成立**（TL;DR 已记）：若走 ADR-0029 迁移，换任何框架照搬同样的数据面
   扫描写法，0.8pp 的 utility 份额原样带过去——实测归因**反向证明**重写解决不了余下大头。
4. 口径边界（如实注明）：DWM 侧的透明窗合成成本是系统进程开销，不在「任务管理器进程页面板
   进程组」的账上（SLO 口径本身如此）；对照组 B 的 0.189% 只覆盖 electron 侧成本，故 ~0.19pp
   是「进程组内结构性份额」的读数，不是机器全域合成成本。
