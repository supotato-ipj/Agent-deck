# 工单250 取证：原生任务栏的保留带能否被释放（spec #236 最大化收栏的产品级缺口）

> 2026-10-23，本机真机实测（Win11，主屏 2560×1440 物理像素，DIP 缩放 1.0）。
> 探针（仓外一次性取证件，不入库）：`D:\test-folder\t250-probes\probe-native-appbar.js`，
> 一律经 `accept-guard` 托管执行（`guard.mjs hold --as mcode --purpose selftest -- node <probe> <mode>`）。

## TL;DR

- **原生任务栏的 48px 保留带不在 AppBar 登记表里**，它是 shell 自己算的工作区项。
  对原生 `Shell_TrayWnd` 句柄发 `ABM_REMOVE`、发「空矩形 `ABM_SETPOS`」、`SW_HIDE` 隐藏窗口，
  **工作区底边纹丝不动**（恒 1392）。⇒ **「释放原生保留区」这条路在本机不存在**。
- ⇒ spec #236 的核心承诺（用户故事 10/11：最大化窗铺满整屏）**在当前实现下没有兑现**：
  收栏只释放了**我方那一份** AppBar 登记，工作区数值不变。
- **这是产品级缺口，不是测试问题**：工单244 把 51 电池 P6 段钉在「AppBar 注册层」
  （`taskbar-retract` 的 `appBar=removed` + `taskbar-appbar-removed`）是**如实口径**，
  本取证与之一致。
- 附带查实一处**独立缺陷**：`app/src/main/taskbar/appbar.ts` 的 `ABM_SETPOS` / `ABM_QUERYPOS`
  **常量写反了**（SDK `shellapi.h`：QUERYPOS=2、SETPOS=3；仓库写的是 SETPOS=2、QUERYPOS=3）
  ⇒ 现行「协商」实际是「先落位、后只读提议」，系统裁剪那一步从未生效。本票未改（越界），
  留待裁决。

## 工作区到底是什么算出来的（实测模型）

```
工作区 = 屏幕矩形 − ( AppBar 登记表内各条保留区的并集  ∪  shell 自算的原生任务栏保留带 )
                          └── 第一项：SHAppBarMessage 能改 ──┘   └── 第二项：SHAppBarMessage 改不动 ──┘
```

### 探针方法学（为什么这组数据可信）

结论依赖「AppBar 登记表**能**改工作区」与「原生那条**不在**登记表里」两件事，
故各配一组对照：

| 对照 | 手段 | 期望（若 AppBar 机制生效） | 实测 |
|---|---|---|---|
| **阳性对照** | 我方 AppBar 窗口**带真实尺寸与位置**（底边 96px 带 `[0,1344,2560,1440]`） | 工作区底边 1392 → **1344** | ✅ **1344**（机制生效） |
| **阴性对照** | 对原生 `Shell_TrayWnd` 句柄发 `ABM_REMOVE` / 空矩形 `ABM_SETPOS` | 若原生那条在登记表里 → 底边应放回 1440 | ❌ **仍 1392**（不在登记表里） |

> 探针迭代留痕：首轮探针用 **0×0 的窗口**注册 AppBar，系统按 `APPBARDATA.rc` 算了提议矩形
> 却**不落保留区**（工作区纹丝不动）——那是探针的伪因，不是系统行为；改用与保留带同尺寸同
> 位置的窗口后保留区如期生效（阳性对照）。同批还发现**顶边**（`ABE_TOP`）的 AppBar 在本版
> Windows 上不落保留区（底边正常）——与本票结论无关，仅备录。

## 候选方向的查证与裁决

### (a) 对原生 `Shell_TrayWnd` 发 `ABM_REMOVE` 注销它的保留区登记 —— **否决**

- **MSDN 语义**：`SHAppBarMessage`（[learn.microsoft.com](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shappbarmessage)）
  —— `ABM_NEW (0x0)`「Registers a new appbar…」、`ABM_REMOVE (0x1)`「Unregisters an appbar,
  removing the bar from the system's internal list」、`ABM_QUERYPOS (0x2)`、
  `ABM_SETPOS (0x3)`、`ABM_GETTASKBARPOS (0x5)`「Retrieves the bounding rectangle of the
  **Windows taskbar**」、`ABM_GETAUTOHIDEBAR (0x7)`、`ABM_SETAUTOHIDEBAR (0x8)`、
  `ABM_GETAUTOHIDEBAREX (0xB)`。文档**未**写「hWnd 必须属调用进程」，但也**未**承诺
  跨进程可注销——语义上 `ABM_REMOVE` 是「把这条 appbar 从系统内部清单里摘掉」。
- **本机实测**：`ABM_REMOVE(Shell_TrayWnd)` 返回 1（调用被受理），**工作区底边仍 1392**；
  随后的 `ABM_NEW + ABM_SETPOS` 还原也无任何变化。⇒ 原生那条**不在清单里**，摘不掉。
- **判据补充**：`ABM_GETTASKBARPOS` 返回空矩形、`ABM_GETAUTOHIDEBAREX(原生句柄)=0`
  ⇒ 本版 Windows 的系统任务栏**不参与 AppBar 机制**，其保留带由 shell 自己算。
- **跨进程问题单独回答**：文档未禁止，探针也未证伪跨进程能力（阳性对照用的是本进程窗口，
  跨进程那轮因 0×0 窗口伪因不作数）；但**跨进程与否在本票里是无关变量**——原生那条
  压根不在登记表里，任何进程都摘不掉它。

### (a′) 对原生句柄发「空矩形 `ABM_SETPOS`」（脱锚）—— **否决**

- 语义上比 `ABM_REMOVE` 更温和（记录仍在，只是脱锚），且未注册时是空转、无副作用。
- **本机实测**：工作区底边**不变**（1392，3 秒后复查仍不变）⇒ 原生那条仍不在 AppBar 机制内。

### (b) 让面板的 AppBar 与原生保留区不重叠 —— **否决（数学上不可能）**

- 原生保留带是**底边通栏**（实测 `[0,1392,2560,1440]`），面板的带也在底边通栏。
- 工作区 = 屏幕 − 并集 ⇒ 并集**恒含**原生那条 ⇒ 底边**恒为 1392**。
  面板换边（`ABE_TOP` 等）只会**多**占一条边，不会少掉底边那 48px。
- 附带结论：**面板自己那 48px AppBar 登记在本机对工作区数值毫无额外贡献**
  （原生那条已覆盖同矩形）——它当前只提供「AppBar 注册层」的可观测面与协商账；
  真正决定底边 1392 的是 **shell 那条**。

### (c) `ABM_GETAUTOHIDEBAREX` / `ABM_SETAUTOHIDEBAR` —— **否决（机制无效果 + 违反 C1 纪律）**

- **MSDN 语义**：`ABM_SETAUTOHIDEBAR`「Registers or unregisters an **autohide appbar**
  for an edge of the screen」——它登记的是「某条边的自动隐藏 appbar 槽位」，
  **不是**「把某条 appbar 改成自动隐藏态」。把它用在原生任务栏上 = 改原生任务栏的
  自动隐藏行为 = **改用户的任务栏偏好**，正撞 `50-taskbar-carry` C1 段
  「StuckRects3 Settings 全程字节不变」与「不改原生任务栏设置」的纪律红线。
- **本机实测（沙箱版，只作用在我方 AppBar 上，原生设置零改动）**：把**我方**那条
  AppBar 登记进底边的自动隐藏槽位（返回 1）后，工作区底边**不变**（1392），
  且 `ABM_GETAUTOHIDEBAR(底边)` 仍返回 0 ⇒ 该槽位机制在本版 Windows 上对工作区**无影响**；
  退一步说，即便有影响，用在原生任务栏上也已被 C1 纪律否决。

## 产品结论：spec #236 的兑现程度

| spec 用户故事 | 当前实现的实际兑现 | 判读 |
|---|---|---|
| 10 前台真最大化时任务栏自动隐藏，**窗口铺满整个屏幕** | **半兑现**：栏面退场、唤出条出场 ✓；**窗不铺满整屏** ✗（底边恒 1392，差 48px） | 缺口 |
| 11 收栏时**工作区占位被释放**，最大化窗真正铺到屏幕底边 | **未兑现**：只释放了我方那份**登记**；系统工作区数值不变（原生那条由 shell 自算） | 缺口 |
| 24 弹出的组**叠加在最大化窗之上且不改变其尺寸** | **兑现** ✓：弹组不重注册占位、不触发窗口重排 | ✓ |
| 25 解除最大化 / 前台切走时栏回归并**恢复工作区占位** | **兑现** ✓（常驻态占位照旧生效，恢复路径无回归） | ✓ |
| 3「最大化收栏」术语、12/13/16–22 唤出条族 | 与本票无关，未受影响 | ✓ |

⇒ **「最大化窗铺满整屏」在本机不发生**；收栏目前兑现的是「栏退场 + 占位登记释放 +
唤出条族」，兑现不了的是「系统工作区归还整屏」这一半。

⇒ **这是产品级缺口，不是测试问题**：验收侧没错——51 电池 P6 段把「占位释放/恢复」钉在
AppBar 注册层（可观测面），正是因为「还回整屏」在 48px 栏高 + 原生保留带并存的本机
**不可观测**。取证结论与工单244 的口径一致。

## 遗留与风险

1. **ADR-0015 第 1 条的前提被本取证证伪**：该 ADR 写「注销 AppBar → 工作区占位释放 →
   最大化窗铺满整屏」，实测第二环不成立。ADR 是工单245 的域，本票**未改**（按简报纪律），
   留待 ADR 所有者/编排者裁决措辞。
2. **`ABM_SETPOS` / `ABM_QUERYPOS` 常量写反**（独立缺陷）：`app/src/main/taskbar/appbar.ts`
   现写 `ABM_SETPOS = 2` / `ABM_QUERYPOS = 3`，而 Windows SDK 10.0.26100.0
   `um/shellapi.h` 与 MSDN 均为 `ABM_QUERYPOS = 0x2` / `ABM_SETPOS = 0x3`。
   ⇒ 现行「协商」实为「先 `SETPOS` 落位、再 `QUERYPOS` 只读提议」——系统按当前工作区**裁剪
   提议矩形**那一步从未生效，返回给调用方的是提议而非已生效矩形。本机两者相同
   （提议 == 落位，实测 `[0,1344,2560,1440]`）故现状无可见偏差；但一旦同边出现别的
   AppBar，占位矩形与条带窗几何就会分叉。**本票未改**（越出本票范围，且改动会动几何语义）。
3. **51 电池 P6 段的段注措辞已过期**（`app/accept/` 归工单243/244 的域，本票未改）：
   它把现象归因为「并集模型」，实测更准确的机制是「并集模型 + shell 自算的原生保留带
   （不在 AppBar 登记表内）」。断言本身（工作区底边在收栏/常驻两态同值）**仍然成立且绿**。
4. **顶边 AppBar 不落保留区**（本版 Windows 的怪癖）：`ABE_TOP` 的 AppBar 登记成功但工作区
   顶边不变（底边正常）。与本票结论无关，仅备录（若将来有产品形态想占顶边，需另行查证）。
