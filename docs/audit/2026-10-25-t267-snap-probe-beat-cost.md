# t267 取证：分屏探针一拍（probeSnapWindows）的轮询拍耗时——250ms 三态轮询上的挂载成本口径

> 2026-10-25，本机真机实测（Win11，主屏 2560×1440 物理像素，DIP 缩放 1.0，单屏；当日桌面常态负载）。
> 量测脚本（仓外一次性取证件，不入库——t250/t257/t268 先例）：`D:\test-folder\spec267-notes\t267-probe\snap-probe-beat-cost.mjs`
> （原始逐拍数据 `results.json` 同目录）。经 `accept-guard` 托管执行
> （`guard.mjs hold --as zcode --purpose selftest -- node <脚本>`，租约正常拿放、退出码 0），全程不裸跑、不拉面板。
> 脚本的绑定声明与采集循环**逐字复刻** `app/src/main/taskbar/snap.ts` 的 `bind()` / `probeSnapWindows`
> 廉价路径与全量采集路径（仅去类型）——生产同构量测，非重写。只读 FFI（枚举 + 查询），不改任何窗口状态。

## TL;DR

- **常态成本可忽略**：本机当前桌面（链式枚举扫过 **495** 扇顶层窗、可见 **17** 扇、arranged **0** 扇）下，
  探针一拍（每窗 `IsWindowVisible` + `IsWindowArranged` 两次 user32 调用的廉价路径）平均 **0.374ms**
  （p50 0.351ms / min 0.224ms / max 1.261ms，40 拍）——占 250ms 轮询间隔的 **0.15%**。
- **2048 上限外推（保守上界）**：按实测摊销 ~0.76µs/扫描窗，2048 窗全扫描 ≈ **≤5ms/拍**（约 2% 间隔）——
  与评审给的「忙系统最坏 ~1.6% CPU 量级」同数量级；即便按「每可见窗摊 22µs」的最保守口径（把链式
  行走成本也记到可见窗头上）外推 2048 全可见也只有 ~45ms/拍，仍留 80% 间隔余量。
- **全量采集路径**（成员/追踪窗命中才付：pid/class/exe/title/rect/iconic/traits 七件套）实测 **58.4µs/窗**
  ——Snap 成员常态 0–4 枚、追踪集 ≤ 数枚，整拍增量 <0.25ms，不构成成本级。
- ⇒ `snap.ts` 头注的成本口径由「两次廉价 user32 调用」的无量测措辞改为**引用本审计实测值**；
  「探针挂 250ms 轮询」的既有节奏不动（spec 只锁「持续重查」不锁频率）。

## 实测数据（原始值，全部本机实测）

| 观测 | 值 | 说明 |
|---|---|---|
| 廉价路径一拍（40 拍均值） | **0.374ms** | 逐窗 IsWindowVisible +（可见窗）IsWindowArranged |
| p50 / min / max | 0.351 / 0.224 / 1.261 ms | max 出现在首拍（JIT/缓存预热），后续 39 拍全部 ≤0.564ms |
| 摊销成本（按扫描窗） | ~0.76µs/窗 | 0.374ms ÷ 495 扫描窗（含链式行走 + IsWindowVisible） |
| 摊销成本（按可见窗，最保守口径） | ~22µs/窗 | 0.374ms ÷ 17 可见窗——把链式行走也记到可见窗头上，只作上界 |
| 全量采集（17 扇样本） | **58.4µs/窗** | pid/class/exe/title/rect/iconic/traits 七件套（成员窗命中形态） |
| 2048 窗外推（按摊销） | **≈1.55ms（全不可见）… ≤5ms（全可见，按分解估算）** | 2048×0.76µs ≈ 1.55ms 起步；全可见再加逐窗 IsWindowArranged 边际（~1–2µs/窗） |
| 2048 窗外推（最保守口径） | 45ms/拍 | 22µs×2048——上界之上的上界，仍留 80% 间隔余量 |
| 2048 窗全量采集外推 | 119.6ms/拍 | 仅当 2048 扇**全部**是成员/追踪窗才发生（现实中成员 0–4 枚）——非可达形态，仅列作界 |

## 解读与口径

1. **常态（本机当日桌面）**：0.374ms/拍 ÷ 250ms = **0.15%** 间隔占用；40 拍无一超过 1.3ms。
2. **忙系统上界**：链式枚举的支配成本是「每扫描窗一次 IsWindowVisible + 一次 GetWindow」，
   实测摊销 ~0.76µs/窗；2048 窗护栏下的全扫描 ≈ 1.5–5ms/拍（**~2% 间隔占用**），与评审给出的
   「~1.6% CPU 量级」同数量级。即便在「大量窗常驻」的服务器形态，成本仍在可忽略档。
3. **Snap 成员命中时**：全量采集 58.4µs/窗 × 常态 0–4 成员 ≈ ≤0.25ms 增量——不影响拍预算。
4. **归档动因**（spec #267 R1 评审第 7 条）：域笔记风险 4 明确建议实现票先量测；分支内此前只有
   电池段时长校准（P12 estSeconds 32 等）、无轮询开销量测在案——本审计补该证据，
   `snap.ts` 头注同步改为引用本文件。

## 结论与后续

- `probeSnapWindows` 挂在 250ms 三态轮询上的成本**实测在案**：常态 0.15% 间隔、护栏上界 ~2%——
  「廉价」的定性成立且自此有量测背书（snap.ts 头注已改引本文件）。
- 不引入降频/缓存等收敛手段：成本实测不足以支撑额外复杂度（spec 决策 3 只要求「持续重查」）。
- 边界（如实）：单机单屏、当日负载快照；koffi 调用开销与机器相关，换机重测走本脚本
  （仓外 t267-probe/ 目录）即可复现；2048 全可见与全成员两档外推是**上界口径**，非观测值。
