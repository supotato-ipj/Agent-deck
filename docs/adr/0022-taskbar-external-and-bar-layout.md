# 任务栏外部交互与栏布局：10 个外部方法全档不投影、5 个栏布局写拆「内核插件·栏布局」子行

ADR-0010 排除「面板外的世界」时只列了 12 个方法，其补记「缺口二」承认 14 个 `taskbar/*` 方法按同一判据同样越界，但当时没有改判，把它登记为地图 #66 的雾。ADR-0021 收口「内核插件·策略」子行时进一步明确：那 14 个不是策略开关，不能借策略子行开口，应按「面板外的世界」判据另裁。本 ADR 收口 #277。

开工先校正三处前提，再拍板：**10 个外部世界交互全档不投影；5 个栏布局写（4 个显式方法 + 同族漏数的 `drag-drop`）拆「内核插件·栏布局」子行**——内核 `W`、后端 `W✓ 确 + 预`（可请求本子行会话级）、外部 `W✓ 确 + 预`（无会话级）、投放 `—`、自主管理提案；5 法都是同步栏布局存储写，不挂串行化；同值空转不进闸门；回滚点与审计照常。同时把「控制面 / 内核档插件包受信内部桥 / 内核 UI 直调」三面边界写死，并给 #282 留一条寻址键约束。

## 前提校正

- **14 个不是一类。** `set-app-pinned` / `rec-pin` / `rec-remove` / `rec-restore` 只写 `userData/taskbar-layout.json`，不碰外部世界；它们与 `app-click` / `activate-window` / `app-windows` / `app-new-instance` / `close-window` / `reveal-app` / `rec-click` / `rec-reveal` / `activate-app` / `tray-click` 这 10 个「操作别的应用窗口、启动与托盘回放」的方法不是同一个客体。
- **不可逆性判断有误。** 缺口二写「`close-window`、`app-new-instance`、`rec-remove` 的不可逆性与 `desktop/trash` 同级」——`rec-remove` 有 `rec-restore`，可逆；`app-new-instance` 是外部进程启动，不是数据损坏；真正会丢未保存工作的是 `close-window`。判据应回到 ADR-0010 的「动的是用户文件系统、剪贴板、外部进程」，不是「可不可逆」。
- **`taskbar/drag-drop` 是第 15 个同族漏数。** 它写同一份 `taskbar-layout.json`，并能在推荐组↔应用组之间手钉/解除手钉、重排两个组；原 14 名单与 ADR-0010 补记都漏了它。若只处置 4 个而把 `drag-drop` 留在原「内核插件层」格，agent 仍可经它完成 pin/unpin/重排，绕过新子行；反过来只关 4 个也一样。故它必须与 4 个同进退。这一点也修正票面「14 个」的口径：本票实际裁 15 个方法。
- **`app-windows` 的只读例外不成立。** 它返回 `hwnd + title`（窗口标题）；#282 正在决定非内核档 `taskbar/get-state` 是否剥离 `title` / `tooltip`。把 `app-windows` 开给非内核档等于绕开 #282；而 `taskbar/get-state` 已给应用、推荐、移除名单，读需求不必靠 `app-windows`。
- **三面边界。** 控制面是 agent 面向的投影；内核档插件包的宿主面是**受信内部桥**（`BridgeMethods` 母集减 `app/quit`）；任务栏渲染层经既有 invoke 桥**直调**。控制面「不投影」不等于受信内部桥或内核 UI 不能调——`taskbar-view.ts` / `taskbar-menu-wins.ts` 的直调不变。

## 决策

### 1. 外部 10 个全档不投影

以下 10 法在控制面**所有信任档**都不存在（传输层回 unknown tool，不是 `not_manageable`）：

`app-click`、`activate-window`、`app-windows`、`app-new-instance`、`close-window`、`reveal-app`、`rec-click`、`rec-reveal`、`activate-app`、`tray-click`。

判据是 ADR-0010 的同一条：它们操作的是**别的应用的窗口、启动与托盘回放**，blast radius 超出面板自身。逐族理由：

- `app-windows`：只读，但泄露窗口标题（#282 的射程）；且单独的可寻址读没有管理价值——`taskbar/get-state` 已提供应用、推荐、移除名单。
- `activate-window`：需要 `hwnd`，而 `hwnd` 只能从 `app-windows` 或 `app-click` 的选窗结果拿；这两个都不投影，这条链没有干净起点。
- `activate-app` / `app-click`：前者未运行就启动、后者可启动/最小化；没有「只置前」的干净子集。
- `reveal-app` / `rec-reveal`：启动 Explorer；ADR-0010 已把同动作的 `desktop/reveal` 排除，口径一致。
- `close-window`：向该 exe 的全部窗口投递 WM_CLOSE，会丢未保存工作。
- `app-new-instance` / `rec-click`：外部进程启动。
- `tray-click`：右击只是开菜单，但左击触发的是目标应用自定义的默认动作，面板无法界定 blast radius。

一条总理由：后端与外部 agent 自己就有进程/文件工具，经面板中转去操作别的应用窗口没有正当需求，反而把面板变成「绕过 agent 自身确认机制的一只手」——与 ADR-0010 排除「面板外的世界」的理由同源。

### 2. 5 个栏布局写拆「内核插件·栏布局」子行

以下 5 法是**面板自身状态**的写，不是外部世界：

`set-app-pinned`、`rec-pin`、`rec-remove`、`rec-restore`、`drag-drop`。

它们的持久副作用只写 `userData/taskbar-layout.json`（手钉清单、推荐位显式序、移除名单；`drag-drop` 还会改会话内存序，不落盘），全部可逆（pin/unpin、remove/restore、拖拽换位都有逆操作）。**不并入「布局」行**：`布局` 是桌面项摆位（`layout.json`），栏布局是任务栏内核插件自己的持久状态；拆独立子行还能让会话级授权的作用域不跨到桌面摆位。

宽严矩阵新增一行：

| 客体 | 内核 | 后端 | 外部 | 投放 | 自主管理 |
| --- | --- | --- | --- | --- | --- |
| **内核插件·栏布局（5 法）** | W | W✓ 确 + 预（可请求本子行会话级） | W✓ 确 + 预（无会话级） | — | 提案 |

记号沿用 ADR-0010：`W` = 可写免闸门；`W✓` = 可写带确认闸门；`确` = 确认闸门；`预` = dry-run。回滚点与审计对所有档所有写默认生效，不逐格标。

- **方法自带的护栏保留。** `set-app-pinned` 要求 exe 在当前应用组条目内；`rec-pin` / `rec-remove` 要求 exe 在当前推荐位名单内；`rec-restore` 只操作移除名单；`drag-drop` 要求源条目可拖。这些校验不是开放级，而是寻址面：agent 只能操作当前栏面上看得见的条目，不能注入任意 exe。
- **内核档 `W`**：免确认；回滚点与审计照常（ADR-0010：内核档不因「调用者知情」而免除）。
- **后端档 `W✓ 确 + 预`**：逐次确认；后端可请求本子行的会话级授权。请求本身是一次带闸门的写、进审计、可被用户的收紧设置关掉；授权随会话存亡、绝不落盘，只覆盖请求时该子行的现有 5 法，未来新增不自动继承。
- **外部档 `W✓ 确 + 预`**：逐次确认，**无会话级**（ADR-0010：外部是常驻端点、凭证长期有效，没有「会话」边界）。
- **投放档 `—`**：投放窄面（ADR-0019）只有 `taskbar/get-state`、`host.view` 4 段与自身 `host.config`，本子行不进入。
- **自主管理 `提案`**：不能直接写；批准即一次性授权，落地那次写必须记自主管理档并引用提案 id（ADR-0010 / ADR-0020）。
- **dry-run**：控制面投影的 `dryRun` 返回写入后的 `TaskbarState`，不落盘、不建回滚点、不触发确认闸门；按读侧口径进审计（只读聚合），不记作实际写。`drag-drop` 现有响应只有 `ok/error`，dry-run 的 `TaskbarState` 是控制面新增形态，不改内核 UI 调用。
- **同值空转**：同钉 / 同移除 / 同恢复 / 自落点直接返回当前结果（4 法为 `TaskbarState`；`drag-drop` 保持 `ok:true`，控制面投影可统一附当前 `TaskbarState`）；不进确认闸门、不写盘、不建回滚点。
- **不挂串行化**：5 法都是同步写 `taskbar-layout.json` + 提交内存 + 回推事件，没有在途异步副作用；确认闸门本身异步，但批准后的写同步执行（与 ADR-0021 策略子行同口径）。
- **回滚点与审计**：每条实际写都进审计（谁 / 何时 / 方法 / 参数摘要 / 闸门结果 / 成功失败），写前建回滚点；只有用户能触发还原，调用方不能自己回滚。`drag-drop` 对未钉运行条目的重排只改会话内存序、不落盘，不是可回滚的持久变更；回滚点覆盖布局存储。

### 3. 三面边界写死

| 面 | 拿到什么 | 本决策 |
| --- | --- | --- |
| **控制面**（agent 面向） | 按信任档裁剪的 `BridgeMethods` 投影 | 外部 10 法不存在；5 法按上表开放 |
| **内核档插件包受信内部桥** | `BridgeMethods` 母集减 `app/quit` | 15 法都在，不因本决策收窄 |
| **内核 UI 直调** | 任务栏渲染层经既有 invoke 桥 | 15 法都在，调用点不变 |

「方法不存在」是**控制面投影**的事实，不是 `BridgeMethods` 被删除、不是内核 UI 被禁止、也不是方法被废弃。投放型插件包的窄面（ADR-0019）同样不受影响：它只有 `taskbar/get-state`。

### 4. #282 的寻址键约束

5 法以 `exe`（应用组 / 推荐位 / 移除名单）或 `name`（推荐位拖拽）寻址，身份来自 `taskbar/get-state`。本 ADR 不决定 #282 的完整脱敏字段集，但加一条硬约束：**非内核档 `taskbar/get-state` 必须保留可寻址身份**。

- 推荐保留 `exe` / `name`，只剥 `title` / `tooltip`：后端与外部档本来就能从 `desktop` 段看到绝对路径、从 `sessions` 段看到项目 basename，单独在 taskbar 这里剥 `exe` 并不一致。
- 若 #282 选择剥 `exe` / `path`，它必须为这 5 法提供等价的不透明键（如 `targetKey`），否则这 5 法只能退成内核档——那会重开本决策的寻址面，不能静默发生。
- `title` / `tooltip` / `iconKey` 等其余字段仍由 #282 收口；本 ADR 不预支。

### 5. 读侧不在本票

`taskbar/get-state` 的脱敏归 #282；`taskbar/tray-icon` / `taskbar/status` 是内核 UI 的读侧方法与事件，不属于本票裁的 15 个写/交互方法。若控制面将来要开托盘图标读，按 #282 的口径与快照/事件同口径设计，另开票。

## 票面四问的答案

1. **是否整体越界、有无例外？** 外部 10 个整体越界、全档不投影，无例外（`app-windows` 的只读例外被窗口标题与 #282 否决；`activate-app` 会启动）。4 个栏布局写不属于「面板外的世界」，进入控制面的新子行（连同 `drag-drop`）。
2. **若留在内核插件层列，开哪一档、什么闸门？** 不留在原「内核插件层」行；拆「内核插件·栏布局」子行：内核 `W` / 后端 `W✓ 确 + 预`（可会话级）/ 外部 `W✓ 确 + 预`（无会话级）/ 投放 `—` / 提案。**不沿用**收栏票的「策略写 vs 视图态」区分——本子行是布局写，不是策略开关。
3. **逐个分级还是整族判据？** 两个方法族一个判据：外部交互整体不投影；栏布局写整族一行。不逐个分级。`drag-drop` 是同一族的第 5 法，不是例外。
4. **与内核 UI 直调怎么区分？** 见「三面边界」：控制面是 agent 面向的投影；受信内部桥与内核 UI 直调都不受本决策影响。

## Considered Options

- **15 个全档不投影（含 5 个栏布局写）**：把任务栏布局也当外部世界；但那 4 个只写 `taskbar-layout.json`，违背「碰的是外部世界」判据，也把 charting 时定到最宽的边界悄悄收窄。否决。
- **保留只读的 `app-windows`**：把窗口标题开给非内核档，与 #282 的收紧方向冲突；且 `taskbar/get-state` 已覆盖读需求。否决。
- **保留 `activate-window` 的只置前**：需要 `hwnd`，寻址链起于不投影的 `app-windows` / `app-click`；单独开没有可用入口。否决。
- **保留 `reveal-app` / `rec-reveal`**：它们只启动 Explorer，看似无害；但 ADR-0010 已把同动作的 `desktop/reveal` 排除，开一条会让「面板外的世界」出现方法级回头路。否决。
- **只开 4 个、关掉 `drag-drop`**：agent 能增删不能排序；或若 `drag-drop` 留在原格，则成为绕过新子行的后门。否决。
- **并入「布局」行**：桌面摆位与栏布局是两份存储；并入会让会话级授权与 dry-run 语义跨两个客体，且栏布局是任务栏内核插件自己的状态。否决。
- **把 5 法放进投放窄面**：投放档是最窄的信任档（投放即 RCE、无发布把关）；ADR-0019 已把投放窄面收成 `host.view` 4 段 + `get-state` + `host.config`。否决。
- **不给 dry-run**：可逆 + 回滚点确实能兜底，但布局类写的预览价值高，且本子行新建时一次定进去比以后改契约便宜。否决。
- **给 5 法挂串行化**：5 法是同步存储写，没有在途异步副作用；串行化是空转。否决。
- **现在就把寻址键改成 `targetKey`**：会把 #282 的脱敏决策提前到本票，且要改现有内核 UI 调用；本票只加约束，把键的形状留给 #282。否决。
- **外部档也给会话级**：ADR-0010 已定外部没有会话边界；会话级等于永久授权。否决。
- **按方法逐个定开放级**：同一份存储、同一类逆操作，逐个分级会让矩阵不可审计；方法自带护栏已经承担了方法级差异。否决。

## Consequences

- **ADR-0010**：新增补记（2026-10-25 #277 决完后）登记「缺口二」的收口：10 个外部方法全档不投影；4 个栏布局写 + `drag-drop` 第 5 法拆「内核插件·栏布局」子行；三面边界与 #282 寻址键约束。原矩阵表不改写，保留历史决策。
- **GLOSSARY**：新增**栏布局**词条（与桌面**布局**的存储边界）；**内核插件**词条从「生命周期 + 策略两个子行」更新为「生命周期 + 策略 + 栏布局三个子行」。
- **#282**：收到寻址键约束——非内核档 `taskbar/get-state` 必须保留 `exe` / `name` 或等价不透明键；其余脱敏字段仍由 #282 决定。建议保留 `exe` / `name`、剥 `title` / `tooltip`。
- **ADR-0019**：投放窄面不变（`host.view` 4 段 + `taskbar/get-state` + `host.config`）；5 法不进入。
- **ADR-0020**：自主管理可以对 5 法提案，但不能直接写；批准落地记自主管理档并引用提案 id。
- **ADR-0021**：不重开策略子行；5 法不是策略开关，不能借策略子行开口。
- **实施输入**（控制面尚未落代码）：5 法的投影与格位、确认闸门/会话级授权/dry-run/回滚点/审计、同值空转短路、`drag-drop` 的 dry-run 响应形态；10 法的「不存在」投影与 unknown tool 错误。本 ADR 不产代码。
- **内核 UI 与受信内部桥不变**：15 法仍在 `BridgeMethods`；任务栏渲染层直调、内核档插件包受信内部桥都不受影响。控制面「不投影」只是 agent 面的缺席。
- **验证**：纯决策与词汇变更，无运行时代码；`git diff --check` 与 PR CI 通过即可，不跑真机验收电池（没有运行时行为可验）。

## 补记（2026-10-25，#282 决完后）

ADR-0023 兑现了本 ADR 留给 #282 的寻址键约束：

- `TaskbarStateManaged` 保留 `recommendations[].name` / `exe`、`excluded[].exe`、`apps[].exe`；5 个栏布局写的签名不变，不引入 `targetKey`。
- `TaskbarStateDisplay` 不含 `exe` / `name`；投放档本来就没有 5 个栏布局写，故不影响寻址面。
- `title` / `tooltip` / `path` / `iconKey` / 整个 `tray` 对非内核档剥离。
- `desktop` 段开关不与任务栏身份联动；任务栏行仍可被用户整格收紧。

详见 ADR-0023。
