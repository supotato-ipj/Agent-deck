# 验收电池治理机制：verdict 三态与环境定责、段级清单唯一登记处、CI 校验器执行力、FAIL-ENV 有条件放行的合并门

背景：工单97 验收 8 轮全量 FAIL、基线 commit 同挂（#107），verdict 不可用，合并前置被卡死——环境噪声（面板主进程间歇停摆级联压制输入注入类断言）与测试集无治理（5600+ 行单文件约 25 段无登记、无归属、无时长约束）两个问题互相放大：verdict 失真让人想删段，删段无账可查。本决策把两件事一起治：**verdict 三态与环境定责**恢复噪声下的判读力，**段级清单 + CI 校验器**让测试集增删改有账可查且 mechanically 不可绕过。落点：报告状态机（`app/accept/lib/report.js`）、面板控制模块（`app/accept/lib/panel-control.js`）、段级清单（`app/accept/manifest.json`，唯一登记处）、清单校验器（`app/accept/lib/manifest-check.js`，以 vitest 进 CI）、章法（`docs/agents/battery-governance.md`）。

## 决策一：verdict 三态 + 排除窗环境定责

verdict 从二态（PASS/FAIL）升级三态：**PASS**（无失败）/ **FAIL-CODE**（存在未定责失败）/ **FAIL-ENV**（全部失败已定责环境），映射退出码 **0 / 1 / 2**，verdict 行带三路计数（pass/fail/excluded）与 scope——guard 与自动化编排按退出码分辨三种结局。

定责机制是**排除窗**：面板停摆检出即开窗，窗内失败断言自动改记环境降责排除（附原因与归因），面板重启并验证健康后闭窗。定责不靠事后人工判读，靠「断言对停摆敏感」的结构事实——停摆窗内一切输入注入类断言不可信，这是 #107 八轮全挂的直接教训。panel-control 模块的强退序列（优雅终止 → 整树强杀 → **有界等待并验证进程确实消失**）斩断双面板级联：强退后仍存活报「需重启清障」并中止后续段——被污染的轮次不再产出误导性 verdict。preflight 环境体检（四类已知污染源）在报告开头警示入账：**警示不进三路计数、不拒跑**——它是 FAIL-ENV 的证据链起点，不是断言（若计入则本机常驻覆盖层会让电池永远 FAIL-ENV，合并门形同虚设）。

**退出码歧义的裁决**：电池 crash 路径（无 VERDICT 行）历史上 `app.exit(2)`，与 FAIL-ENV 同码。定夺：**保留同码，判据 = 有无 VERDICT 行**。备选（crash 改独立退出码）被否：退出码是进程级信号，同码不同义的歧义由证据文件消解（VERDICT 行在即三态判毕、不在即 crash），而新增第四个退出码要求全部编排方学习一个新状态，收益不成比例。副电池五块仍二态旧用法（`verdict('PASS'/'FAIL')`，退出码 0/1），三态迁移待其失真成为实际问题时再议——它们的失效面以系统状态/面板存活为主（工单114 盘点：对停摆不敏感），先例上没有 FAIL-ENV 的需求压力。

## 决策二：清单是唯一登记处，代码只报段号

每段在清单登记（段号/工单号/失效面五枚举/估计时长），电池代码只在段起笔报段号（`rep.beginSegment('<seg>')` 一行）——**代码与账本零重复**：元数据改清单、不动代码；段的存在性由双向比对看住。失效面判定口径随清单入库（`_doc`）。存量 67 段一次性归账完成（工单114），六电池 444 判定点的失效面分布（输入注入 80.6%）同时是 #107 失真面的结构性定量证据。

**备选否决**：元数据写代码注释放报告解析——注解与代码同文件演化最「顺手」，但注册处会裂成两份（段存在性看代码、归属看注释），「删段不清账」恰好从裂缝里漏过去。唯一登记处 + 静态扫描双向比对把这条裂缝焊死。

## 决策三：CI 校验器是治理的执行力，不是文档的注脚

清单↔代码双向同步、字段完备性、分电池时长预算全部静态校验，以 vitest 测试形态进现有 CI（真机电池进不了 CI，治理执行力全靠这一层）。**校验器判红的 PR 不可合并**：新段未登记、删段不清账、缺字段、超预算，任何一条都 mechanically 拦下。`--accept-scope` 升级为对清单硬交叉校验（清单在位时未知段号启动即错，不再告警放行）——烧完 7 分钟真机轮才发现声明打错的事不再发生；运行期「声明段未实跑」仍是 WARN，那是合并门「范围段被打断须重跑」的输入信号，不是错误。

## 决策四：FAIL-ENV 合并门——有条件放行

- **PASS（0）直过**：无失败，证据文件照常归档。
- **FAIL-CODE（1）否决**：存在未定责失败即代码问题待解，无例外（是否真回归由基线判别裁决后改账，改账前维持否决）。
- **FAIL-ENV（2）有条件放行**：仅当 **spec 范围段全部实绿**（声明的段在本轮实跑且全过）且 **PR 附环境证据**（preflight 段 + 排除窗账目 + 必要时基线判别结论）才允许合并；**范围段被环境打断（声明了但未实跑）必须重跑**，不允许「范围段也可能过了」的推断。

这个分级的取舍点：环境噪声既不能放过真回归（FAIL-CODE 一票否决不变），也不能无限阻塞有效合并（工单97 八轮卡死合并的形态）。「范围段全实绿」是放行的硬条件——本轮在验的断言必须真的给出过证据，环境只允许污染范围之外的观测。

## 后果与边界

- 机制第一场实战即 #107：噪声环境下产出带 preflight 证据的 FAIL-ENV（工单112/113 真机轮已实证排除窗、强退验证与中止路径），替代原 8 轮不可用 FAIL。
- 强退序列改变了停摆自愈的时序（有界验证最多 +5.8s），无停摆时与现状等价（真机轮 pass 连续三轮上升的等价性实证见 PR #121）。
- 「停摆即杀」的清障策略会摧毁面板内滞后哨兵的 lag 观测（工单117 取证结论）——根因修复票须给哨兵留有界唤醒窗或由数据面代管观测，本 ADR 不裁。
- 章法（增删改三面规矩、flaky 流程、预算流程）见 `docs/agents/battery-governance.md`；词汇表八词见根 `GLOSSARY.md`。
