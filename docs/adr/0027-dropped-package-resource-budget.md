# 独立执行上下文的资源预算：16 包同时在场、每包 128MB 边际内存，超限显式拒绝

ADR-0025 为逐包隔离付了每个投放包一个独立 `webContents` + 独立 session 的代价，但从未给出「能同时跑多少包、单包吃多少内存、超了怎么办」。spec #326 收口票（#341）要求据实测形成明确预算，且超预算行为必须是显式处置而非静默退化。拍板：**同时在场投放包上限 16、每包边际工作集预算 128MB（首版按 24 包/80MB 起笔，C10 实测后按数据修正）；超限的新包显式拒绝（`package_budget_exceeded`）并留事件，不静默丢弃、不偷偷降级渲染。**

## 实测标定

C10 真机段（`332-conversation`，guard 托管）用 0/1/5/10 个零权限投放包读面板**全进程工作集**（`app.getAppMetrics()` 汇总，`diag/memory` 桥接通道同源）：

- 终轮（PASS 66/0）读数：0 包 **896MB**、1 包 **894MB**、5 包 **1314MB**、10 包 **1840MB**；
  每包边际 ≈ **105MB**（0→10 口径 94MB/包、1→5 与 5→10 口径 105MB/包）。
- 基线 = 主进程 + GPU + Utility（数据面/网络）+ 面板与卡片常驻 Tab（Chromium 渲染进程基线本来就 ~100MB，包页在其上很薄）。
- 取 **128MB/包** 为预算上限（约 1.2× 实测）；16 包上限对应约 1.7GB 边际工作集、整机约 2.6-2.8GB 封顶。

读数随每轮的段账目（`NOTE C10 预算实测…`）落在验收证据里，机器换代后按同一段落重新标定。

## 超限行为

- 达到上限后的新包：`status = error`，错误码 `package_budget_exceeded`（契约目录登记），事件 `dropped-package-budget-exceeded`（含 `live` 与 `cap`）。
- 拒绝是**每轮重试**的：腾出槽位（卸载/停用/删包）后下一次 rescan 自动补位，不是永久拉黑。
- 在场计数按「本轮扫到的 id 集」算：磁盘上已删但尚未在轮末清算的包不占预算，删包即时释放槽位。
- 崩溃（`crashed`）的包仍占着 `webContents`，计入预算——不自动重挂在预算语义上也不白占。

## Considered Options

- **软限 + 静默降级（少渲染/复用上下文）**——违反 ADR-0025 的隔离前提，也让用户看不出为什么某个包「装上了没显示」；拒绝。
- **按内存动态驱逐（LRU 卸载最久未用包）**——桌面组件是常驻物，驱逐会造成不可预期的消失；首版不做，等有真实超额使用再议。
- **只给文档不给硬门**——预算就成了口号；超限时必须有一致的、可审计的拒绝面。

## Consequences

- 上限是常量（`budget.ts`），与契约目录 `resourceLimits` 同源投影；测试可注入更小上限做矩阵验证。
- 每包 128MB 是**上界**不是目标；实测贴近上限时应先查包页资源问题，再考虑调预算。
- 未来若引入共享渲染或包间复用，须先推翻 ADR-0025 的逐包上下文决策，本预算随之重标。

## 增补段：内存半边的运行时闸门（工单344，2026-11-08 grill 定案）

数量半边的硬门（第 17 个包当场拒绝）落地后，内存半边仍只是「挂墙上的尺」——没有任何告警与处置。本段把内存半边从标尺补成闸门（**包内存哨兵**，GLOSSARY 词条），是对上述裁定的补全，不是新取舍。

**两级处置参数**（`budget.ts` 单一正典，阈值与契约 `resourceLimits` 同一把尺）：

- 采样每 **10 秒**一轮（`MEMORY_SENTINEL_INTERVAL_MS`），仅在有在场投放包时跑（无包停表，开销有界）；
- 某包**首次**越过 128MB 预算线 → 告警一次（用户可见条带 toast 5s 自收 + 存证事件，含读数/阈值）——留给用户自己动手的窗口；
- **连续 3 轮**仍超线（10s×3 ≈ 30 秒滞回确认窗，`MEMORY_SENTINEL_CONFIRM_ROUNDS`）→ 显式停用：照抄既有停用路径（幂等 deactivate 强制销毁渲染进程）、包 `status=error`、错误文案带 `package_memory_exceeded`（契约目录 ERRORS，与 `package_budget_exceeded` 同族）、停用审计事件含读数/阈值/轮数（reason=`memory-budget-exceeded`，与 `permission-revoked` 同构）；
- 中断回落线内即重新计数（滞回滤掉瞬时尖峰）；停用后**包文件不动、账不删、rescan 不救回**——用户重新投放一次/改码换代 = 显式恢复，与崩溃包「不重挂、显式恢复」完全同一套体验。

**计量口径**：Electron 全进程指标按 pid 读包进程工作集（与 `diag/memory` 同一事实源），**不做边际基线减法**——包的独立渲染进程工作集直标 128MB（本 ADR 实测每包边际 ≈105MB 与包进程自身工作集基本重合，105→128 的 1.2× 余量配合滞回防误杀）。pid↔包对照落投放包宿主层（webContents → OS pid 现成手法，换代即换 pid），pid 是 Electron 层事实，不进纯逻辑 identity 登记表。

**放行语义**：采样时某包 pid 查不到读数（进程刚崩、时序缝隙）→ 不处置、只留证——宁可漏报不误杀。

**模块形态**：哨兵核心判账是纯逻辑账本（`memory-sentinel.ts`，不 import Electron；输入「读数 + pid 映射 + 参数」、输出「告警/停用动作」），Electron 采样与宿主 pid 记录是薄壳，生产装配注入；**唯一新缝 = 内存读数函数注入**，与既有「包数上限可注入」同族。真机端到端由 `332-conversation` 电池 C12 段存证（告警→停用→账不删→toast→面板不崩）。

## 增补段：判据尺切换私有提交内存口径（工单452，2026-11-13 口径裁决）

C12 段五轮三红（2026-11-10）的诊断定谳（[#452 诊断评论](https://github.com/supotato-ipj/Agent-deck/issues/452#issuecomment-6828820912)，机制级 harness + guard 托管真电池双证）：哨兵唯一计量口径=包渲染进程**工作集**（`memory.workingSetSize`），是 OS 可随时回收的可变指标——发作性修剪扫击一拍内 165MB→2MB（streak 重置→90s 无停用，恰好 1 alert + 0 停用）；持续深压（avail 0.3-0.8GB）下工作集配额被夹死线下（116-123MB<128MB）→**连告警都不出**（L2-2 端到端复现）。产品面同病：真实失控包在深压下被现口径漏报。

**裁决（2026-11-13 用户拍板，候选②）**：判据尺读数改取同一次 `getAppMetrics()` 的 `memory.privateBytes`（win32 现成字段，KB→bytes）——私有提交内存不受工作集修剪影响，扫击/深压/释放全形态稳态（15 块 hog 实测 88-99MB，波动<10%）。阈值按私有口径重标定 **80MB**（`PACKAGE_SENTINEL_PRIVATE_MEMORY_BUDGET_BYTES`）：包渲染进程私有基线实测 ~37-40MB，80MB ≈ 基线×2 余量（旧工作集口径余量 23MB≈128−105，私有口径 43MB 相对更宽，不收紧正常包）。

**双尺并存（不合并、不换算）**：判据尺（本段哨兵，80MB 私有口径）回答「这个包失控了吗」——只经事件载荷 `thresholdBytes` 透出，不进契约目录；容量尺（上文 128MB 工作集口径）回答「这台机器还能装几个包」——继续服务 `resourceLimits` 投影、C10 系列与 16 包容量规划。两把尺单位、口径、回答的问题都不同，不许互相换算。

**随动与不动**：哨兵端口 `readWorkingSetBytes` 更名 `readPrivateBytes`（缝语义显影），纯逻辑账本零改动（只吃数字）；C12 段 hog 配重 15→18 块（~72MB 堆，私有读数期望 ~100-112MB、深压地板 ~96-100MB，对 80MB 线全形态余量 ≥16MB），断言语义零漂移（battery-governance 改段报备：理由=口径切换定谳 + 配重核对，理由随改动 commit 入库）；C10 段 128MB 断言=容量尺正典，零改动；停用补偿文案走 facts 注入，零改动。候选③（段首水位 preflight）不做——诊断实证其对扫击形态预测力差、防不住；深压第二形态的漏报面已被口径切换消除。旧工作集口径的史实保留于上文工单344 增补段，不改写。
