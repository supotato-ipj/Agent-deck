# 独立执行上下文的资源预算：16 包同时在场、每包 128MB 边际内存，超限显式拒绝

ADR-0025 为逐包隔离付了每个投放包一个独立 `webContents` + 独立 session 的代价，但从未给出「能同时跑多少包、单包吃多少内存、超了怎么办」。spec #326 收口票（#341）要求据实测形成明确预算，且超预算行为必须是显式处置而非静默退化。拍板：**同时在场投放包上限 16、每包边际工作集预算 128MB（首版按 24 包/80MB 起笔，C10 实测后按数据修正）；超限的新包显式拒绝（`package_budget_exceeded`）并留事件，不静默丢弃、不偷偷降级渲染。**

## 实测标定

C10 真机段（`332-conversation`，guard 托管）用 0/1/5/10 个零权限投放包读面板**全进程工作集**（`app.getAppMetrics()` 汇总，`diag/memory` 桥接通道同源）：

- 终轮（PASS 66/0）读数：0 包 **896MB**、1 包 **894MB**、5 包 **1314MB**、10 包 **1840MB**；
  每包边际 ≈ **105MB**（0→10 口径 94MB/包、1→5 与 5→10 口径 105MB/包）。
- 基线 = 主进程 + GPU + Utility（数据面/网络）+ 面板与卡片常驻 Tab（Chromium 渲染进程基线本来就 ~100MB，包页在其上很薄）。
- 取 **128MB/包** 为预算上限（约 1.2× 实测）；16 包上限对应约 1.7GB 边际工作集、整机约 2.6-2.8GB 封顶。

读数随每轮的段账目（`NOTE C10 预算实测…`）落在验收证据里，机器换代后按同一段落重新标定。

## 超限行为

- 达到上限后的新包：`status = error`，错误码 `package_budget_exceeded`（契约目录登记），事件 `dropped-package-budget-exceeded`（含 `live` 与 `cap`）。
- 拒绝是**每轮重试**的：腾出槽位（卸载/停用/删包）后下一次 rescan 自动补位，不是永久拉黑。
- 在场计数按「本轮扫到的 id 集」算：磁盘上已删但尚未在轮末清算的包不占预算，删包即时释放槽位。
- 崩溃（`crashed`）的包仍占着 `webContents`，计入预算——不自动重挂在预算语义上也不白占。

## Considered Options

- **软限 + 静默降级（少渲染/复用上下文）**——违反 ADR-0025 的隔离前提，也让用户看不出为什么某个包「装上了没显示」；拒绝。
- **按内存动态驱逐（LRU 卸载最久未用包）**——桌面组件是常驻物，驱逐会造成不可预期的消失；首版不做，等有真实超额使用再议。
- **只给文档不给硬门**——预算就成了口号；超限时必须有一致的、可审计的拒绝面。

## Consequences

- 上限是常量（`budget.ts`），与契约目录 `resourceLimits` 同源投影；测试可注入更小上限做矩阵验证。
- 每包 128MB 是**上界**不是目标；实测贴近上限时应先查包页资源问题，再考虑调预算。
- 未来若引入共享渲染或包间复用，须先推翻 ADR-0025 的逐包上下文决策，本预算随之重标。
