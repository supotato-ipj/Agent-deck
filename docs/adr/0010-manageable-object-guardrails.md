# 可管理对象的护栏分级：宽严矩阵按档单调、闸门分级组合、护栏是协作性而非强制性

ADR-0009 定了控制面的**形状**（`BridgeMethods` 的投影、`BridgeService` 单点分派、四信任档、禁止代发），并把「各档对各类客体开到读还是写、写要不要闸门」留给本决策。拍板：客体侧的分级叫**开放级**（与「信任档」正交，后者分的是「谁在调」，前者分的是「能调到什么程度」），取四值——`不在投影内`（方法不存在）/ `只读` / `可写` / `可写(带闸门)`；四档在每一个客体列上**单调不增**，宽严顺序是 **内核 > 后端 > 外部 > 投放**（不是 ADR-0009 列举的顺序，理由见下）；**自主管理不入序**，它的形状不同——不能直接发起写，只能产出**提案**，用户批准即一次性写授权，且落地那次写的信任档必须记为自主管理档、审计必须引用提案 id，缺一条即构成 ADR-0009 禁止的**代发**。闸门是**分级组合**而非单选：**回滚点**做地基（所有写、所有档默认生效，含内核档）、**确认闸门**只给不可逆与大影响面的格子且**内核档免**（内核 UI 的调用者就是知情人本人）、**dry-run** 只给布局列、**串行化**给所有有在途异步副作用的写且与身份无关、**审计**覆盖读与写（只读聚合记、写逐次记，agent 只能读自己那一档）。`config` 拆成「观感与检索」与「信任根与持久化」两组，后者的 `plugins.dir` 与「护栏配置」享受特殊待遇——`plugins.dir` **全档不投影含内核档**（它定义投放档的信任边界本身，改它等于把待装载区整个搬走），护栏配置**仅内核档可写**（否则单向收紧可被 agent 自己撤销）。只读侧：`panel/snapshot` 按**段级**裁剪（同一方法按档返回不同段集，沿用 capability「少给而非不给」的先例），事件与快照视作同一只读客体的两种交付形态、护栏口径完全一致，`search/results` **全档永不进**（它是 Listary 全盘索引）。最后必须写明效力边界：**护栏是协作性的，不是强制性的**——矩阵只约束经控制面发起的写，而外部与后端 agent 都持有自己的文件工具，能直接改 `userData`，绕过全部门禁。

## 前提校正

本决策开工时探明三处与 ADR-0009、地图 #66 记录不符的事实，先校正再决策：

- **方法表是 27 个，不是 25 个**（4 读 + 23 写，`app/src/shared/contract.ts:226-373`）。ADR-0009 的 `:14`、`:16` 与地图 Notes 均记为「25 法 = 4 读 + 21 写」。（工单97 复核编注：现表已 38 法——taskbar 交互族 12 法入表（工单51-58）、`desktop/pin`·`desktop/unpin` 退役、增 `settings/set-card-enabled`（工单101），行号现为 `app/src/shared/contract.ts:331-535`；上文 27 是本决策开工时计得的口径，ADR-0009 `:14` 已同步 38。）
- **四类客体里有两类在母集里几乎是空的**：**插件包类 0 个方法**（`PluginHost` 有 `rescan()` / `unload(id)`，`app/src/main/plugins/service.ts:134,168`，但从未经桥暴露；安装 = 往用户根放目录、卸载 = 删目录，纯文件系统操作），**config 类只有 2 个写方法**（`settings/set-card-opacity`，以及 `taskbar/set-enabled` 顺带写 `config.taskbar.enabled`）；面板几何、天气经纬度、搜索引擎选择、五工具映射、自启项**全无写方法**（layout 与 weather 是构造期只读注入，`app/src/main/services/bridge.ts:31-32`）。即 ADR-0009 说的「投影」对这两类客体**投出来是空集**，「控制面是 `BridgeMethods` 的一个投影」这句判断本身不再成立，本 ADR 将其修订为「**以既有契约的投影为主、允许受控新增，约束是单点分派与一份契约不变**」。
- **「禁用任务栏即掀掉整个桌面承载层」不成立，但目标形态下的真实后果更具体**。实测：`taskbar/set-enabled(false)` 是**纯视图态**还原（`ShowWindow(Shell_TrayWnd, SW_SHOW)`，不写注册表、不碰 AppBar/StuckRects，`app/src/main/taskbar/native.ts:14-20,58-69`）、**不卸载 cordis 插件**（内核插件无任何运行期卸载路径，「禁用」与「卸载」是两件事）、**与桌面承载层零耦合**（`grep taskbar app/src/main/desktop/` 无命中；原生桌面图标的隐藏归外层守卫的 `IconCarry`，随守卫生命周期）、**运行时可逆不需重启**、同值幂等（`app/src/main/services/taskbar.ts:51-63`）。三层崩溃兜底真机 PASS（`before-quit → dispose()`、外层守卫按视图事实还原、detached 还原守护），生产自启走守卫故不会卡在隐藏态。**但按 GLOSSARY 的目标形态**（其栈顶是 `feat/taskbar-takeover`，已验证包含其余八条 taskbar 分支；master 上条带只有 START + TASK VIEW 两个按钮，GLOSSARY 的描述领先于 master），托盘宿主自工单56 起**无条件常驻**（该分支 `app/src/main/services/dataplane.ts:84` 的闸门从 `init.traySpike` 改成 `init.tray`，而 `index.ts:172-174` 传的是 `options.traySpike ? {corpusFile} : {}`，`{}` 恒真），以 `RegisterClassExW('Shell_TrayWnd')` 竞争同名窗口吞下全部 `NIM_*`（该分支 `app/src/main/trayhost/host.ts:132-162`），而 `setEnabled` 与 `destroy('disabled')` **零托盘处理**、`trayHost.stop()` 是**死代码**（全仓无调用点）、唯一的交还广播只存在于验收脚本（`app/accept/tray-spike.js:184-195`）——**禁用期间第三方托盘图标既不回原生区域也不可见，用户彻底失去入口**。这才是任务栏那一格的真风险，不是「掀桌」。

## 宽严矩阵

记号：`—` 不在投影内（方法不存在）｜`R` 只读｜`W` 可写免闸门｜`W✓` 可写带闸门（**确** = 确认闸门、**预** = dry-run、**串** = 在途串行化）。**回滚点与审计对所有档所有写默认生效，不逐格标。**

| 客体 | 内核 | 后端 | 外部 | 投放 | 自主管理 |
| --- | --- | --- | --- | --- | --- |
| **插件包** | W（待装载区必经，闸门免） | W✓ 确 + 待装载 | R | — | 提案 |
| **布局** | W（含 `desktop/reset-layout`） | W✓ 确 + 预 | W✓ 确 + 预 | R | 提案 |
| **config·观感与检索** | W | W | W✓ 确 | — | 提案 |
| **config·信任根与持久化** | 五工具映射 / 自启项 / 护栏配置 = W；`plugins.dir` = **—** | — | — | — | — |
| **内核插件层** | W（免确，**串 + 原子性照常**） | W✓ 确 + 串 | W✓ 确 + 串 | R | 提案（批准即「用户显式发起」） |
| **只读快照与事件** | 8 段 | 8 段 | 7 段（无 `weather`；`desktop` 用户可单段关） | 4 段（clock / hardware / layout / settings） | 8 段（**必须经控制面**） |

**config 两组的划分**：观感与检索 = 卡片透明度 / 面板几何 / 天气经纬度 / 搜索引擎选择；信任根与持久化 = 五工具映射（会话扫描根）/ `plugins.dir`（插件根）/ 自启项（Startup 的 `.lnk`）/ 护栏配置（用户的收紧设置本身）。

**单调性**：每个客体列上开放级随「内核 > 后端 > 外部 > 投放」单调不增。后端档与外部档在布局列、内核插件层列同为 `W✓`，二者的宽严差由**会话级授权**体现（见下）。单调是刻意选的：它让 Q「用户可再关小」表达为「把切点往左移」，并给出一个可审计的不变量——外部档能做的，后端档一定能做。

**方法级例外，只往严的方向，不破列级单调**：

- `desktop/reset-layout`：**外部与投放不投影**。它是布局列里唯一不可逆且无兜底的方法（清全部显式摆位并落盘，`app/src/main/desktop/desktop.ts:463-468`，无 undo），而且今天**连渲染层确认都没有**（`app/src/renderer/main.ts:1380-1386`）——渲染层唯一的确认浮层只保护 `desktop/trash`（`:897-957`）。
- `taskbar/system-action`：**仅内核档**。合成按键弹开始菜单 / TaskView 会抢用户前台，零管理价值。
- `app/quit`：**全档不投影**。没有任何操作需要重启面板（任务栏切换运行时可逆、插件热重载），ADR-0009 `:15` 已把它列为投影之外。
- `desktop/icon`：与 `desktop` 段**绑定同口径**（它是该段的附属，含用户文件的图标）。
- `search/results` 事件：**全档不投影**。

**会话级授权**：确认闸门逐次为默认，但带闸门的格子允许 agent **请求**会话级授权，该请求本身是一次带闸门的写（进审计、可被用户的收紧设置关掉）。**外部档不给会话级授权**——它是常驻端点、凭证长期有效，「会话」这个概念在它身上不成立，给了等于永久授权。**会话级授权随会话存亡、绝不落盘**：一旦持久化就变成跨会话的长期凭证，与外部档的常驻凭证无异，ADR-0009 定的「档位由凭证发放路径区分」会漏掉一档。

**只读段集**（探针实证的敏感度）：`clock` / `hardware` / `layout` / `settings` / `plugins` 低敏（`hardware` 不含 CPU/GPU 型号、序列号、MAC；`settings` 只有 `cardOpacity`，`config.json` 里的 `search.port`、`plugins.dir`、`tools` 均不入快照）；`sessions` 中敏（无标题、无正文、无 prompt、无 token 数，`project` 仅目录 basename）；`weather` **高敏**（显式经纬度，`app/src/main/config.ts:155` 默认北京）；`desktop` **高敏**（全部桌面文件名 + **绝对路径**，内含 Windows 用户名）。外部档不给 `weather` 是因为经纬度对「管理面板」零价值；给 `desktop` 是因为它是布局客体的读侧，看不见桌面项却要移动它们是危险的盲写——但用户可按段单独关掉它。

**新增约束（把 ADR-0009 的「投放档 `invoke` 必须受裁剪」扩到 `view`）**：插件包 manifest 的 capability **只能在所属信任档的段集上限内声明**。今天没有档级上限——capability 是 manifest 自己声明的七个段名白名单（`app/src/shared/contract.ts:151-156`，注意 `plugins` 段不在表内，故永不下发给插件），未知能力串静默丢弃（`:171`），裁剪发生在渲染进程（`app/src/renderer/plugins.ts:90-97` 的 `viewFor()`，「少给而非不给」）。

## 护栏机制

- **回滚点**（新词；不复用已退役的「布局快照」）：控制面在一次写之前留下的、可由用户单点还原的状态副本。**只有用户能触发还原，agent 不能自己回滚**——否则一次写加一次自我回滚能在用户看不见的情况下互相抵消，审计的价值当场归零；agent 要改回去就再发一次反向写，同样过闸门、进审计、建回滚点。保留个数与保留期交实施（既有先例：`app/src/main/usage/log.ts` 的 90 天滚动清理）。**取样时机必须在写入前一刻**，不能在会话开始时（见「不得整份回写」）。
- **重新引入回滚的正当理由**：「布局快照」于 2026-09-25 退役，针对的是「外部世界会漂移我的图标坐标」这个**已随桌面项改自绘而消失**的威胁；回滚点针对的是「受控写入方自己写坏」这个当时**根本不存在**的威胁（那时没有任何外部写入方）。威胁模型换了，不是同一机制复活。而它现在是必需的：`layout.json` 结构只有 `{version:1, pinned[], dock[], docs[]}`、version 恒为字面量 1、**无 migration**（`app/src/main/desktop/layout-store.ts:7-17`），JSON 损坏时**静默回退出厂态且下次保存覆写原文件**（`:20-27`）——即「损坏自愈」等于用户全部摆位永久丢失；`config.json` 的字段级校验是 warn + 回退默认（`app/src/main/config.ts:131-415`），顶层解析失败时整体回退默认且不覆写（`:438-449`），但**回退之后的下一次透明度滑杆或任务栏开关操作会把内存 config 整份写回磁盘**（`app/src/main/services/settings.ts:46`、`app/src/main/services/taskbar.ts:57`），用户原值随之被静默冲掉。全仓无 `.bak` / backup 写路径、无 undo、无 dry-run、无审计。
- **确认闸门**：只给不可逆与大影响面的格子。**内核档免**——确认闸门服务于「让不知情的人知情」，而内核 UI 的调用者就是知情人本人。**超时即拒绝，同时把该请求转入提案队列**，用户回来后可一次批准：这使「同步闸门」与「异步提案」统一成一条路径，也避免了无限阻塞（MCP 客户端有自己的超时）与「超时降级为 dry-run」（那会让 agent 拿到一份它本不该拿到的预演数据）。呈现形式沿用 ADR-0009 的口径：闸门装在控制面内，面板 UI 弹窗只是它的**呈现形式**；渲染层现有那个自绘确认浮层**不可复用**为服务端护栏（全仓无 `dialog.showMessageBox`，桥接层直接调 `desktop/trash` 会绕过它）。
- **dry-run**：只给**布局列**，且实际只服务后端档与外部档（内核 UI 的拖拽摆位本来就实时可视）。插件包类的预演毫无意义（待装载区里的包不执行）、config 类的预演就是「显示新值」，已包含在确认闸门的呈现里。
- **串行化**：对有在途异步副作用的写强制生效，**与身份无关**（内核档照常）。理由是一个九个 taskbar 分支**一处都没修**的缺陷：`w.once('closed')` 闭包无身份校验就把控制器级 `win` 置空（master `app/src/main/taskbar/window.ts:150-155`；`feat/taskbar-takeover` 同处 `:256-267`，且该分支还在这个闭包里加了 `removeAppBar(appBarHwnd)`，而 `appBarHwnd` 是控制器级共享变量、此时已指向新窗句柄）。「关 → 开」快速连切时旧窗 `closed` 回调晚到会抹掉新窗句柄，后续 `destroy()` 因 `if (!win) return` 够不到它，造出孤儿置顶条带——而 ADR-0007 `:30` 已实证与可见原生栏同矩形重叠**无文档化稳定解**。渲染层 toggle 无防抖、无在途闸门（`app/src/renderer/main.ts:1363-1377`），人类手速撞不出，agent 可以在几十毫秒内连发两次。
- **`taskbar/set-enabled(false)` 的语义契约**：必须**原子完成**「销渲染面 + 交还托盘宿主 + 还原原生栏」，缺一项即视为失败并回滚。这不是实现细节而是该方法在控制面上承诺什么；把 `trayHost.stop()` 从死代码接回 `destroy('disabled')` 是它的实施前提。
- **不得整份回写**：控制面的任何写必须**读-改-写**。在只有面板自己写的世界里，整份回写只是「吞掉外部手改」的小瑕疵；控制面一旦对外开放就成了并发写者问题——agent 读 config、用户手改 config、agent 写回，用户那次手改被静默吞掉，而审计里看不出来（记的是 agent 那次写，它自己是成功的）。master 的 `setEnabled` 还会用 `taskbar:{enabled}` **整段替换**抹掉 `hiddenButtons` / `metrics`（`feat/taskbar-takeover` 已修为 `persist()` 共写）。
- **待装载区**：经控制面写入的插件包**先落待装载区**（不被 `fs.watch` 看见），闸门通过后才移入用户插件根生效；**用户手动投放的路径语义不变**（工单10 的投放即热插拔是插件体系的核心体验，不该被控制面的护栏拖累）。这条是必需的，因为插件包写入的后果**不止于那次写入**：投放进用户根约 **300ms 后在渲染进程执行任意 JS**（`app/src/main/plugins/watch.ts:18,36` 的 recursive watch + 300ms settle，无签名、无用户确认、无隔离；校验只有 manifest 契约检查，坏 manifest 进 error 态、`ready()` 抛错则摘除实例仅 `console.warn`，`app/src/main/plugins/service.ts:252-260`），而该 JS 拿到的 `invoke` 是**未裁剪全表 27 方法**（`app/src/renderer/plugins.ts:104-105` 的 `hostOf` 直接透传，只有 `view` 按 capability 裁剪）。**回滚点对这一类单独失效**——它能撤掉那个包，撤不掉那个包在用户点回滚之前已经干过的事（例如调 `desktop/reset-layout` 清光摆位、调 `taskbar/set-enabled(false)` 关栏），所以必须有事前闸门，且写入与生效之间必须有一道控制面掌握的卡。
- **提案**：自主管理产出的、待用户批准才落地的变更意图。**带过期时间，过期作废；批准后的授权是一次性的，用过即失效**——一次性是必需的，提案机制的正当性全押在「授权来自用户的批准动作」，一次批准若能重复使用就变成长期凭证，与外部档的常驻凭证无异。`proposals/approve` **只能存在于内核档、且调用方必须是用户交互**，否则 agent 自己批准自己的提案，整个机制形同虚设。落地那次写的信任档**必须**记为自主管理档、审计**必须**引用提案 id，缺一条即视为**代发**。
- **审计**：覆盖读与写。只读**聚合记**（档 × 方法 × 段集 × 时间窗 计数），写**逐次记**（谁 / 何时 / 哪个方法 / 参数摘要 / 成功失败 / 闸门结果）。只读必须覆盖，否则「外部 agent 一直在读我的桌面绝对路径与经纬度」这件事毫无痕迹，而段级裁剪是否真的生效也无从验证；但 `panel/changed` 是 **1Hz** 推送（数据面子进程 1Hz 发 `dataplane/snapshot` → `bridge.push()`，`app/src/main/services/bridge.ts:36-37,165-167,201-205`），逐次记会每秒一条、瞬间失去可读性。**agent 能读审计，但只能读自己那一档的记录**——可见性按信任档切，与段级裁剪同构，实施上可复用同一个裁剪点。现成钩子是 `DECK_EVENT_LOG`（`app/src/main/panel-ipc.ts:9-24,78-81`），但只有验收电池设这个环境变量、生产关闭，且只记事件类型、**不记调用方身份**——「记什么」有形状可扩，缺的正是四档模型第一次引入的那个「谁」。既有使用日志撑不起审计：`userData/usage` 按天 JSONL 每条只有 `{ts, exe}` 两字段（`app/src/main/usage/log.ts:13-16,44-52`，刻意不含窗口标题见 ADR-0002），不记面板内任何写操作。
- **用户可收紧的最小单位** = 「档 × 客体」整格 **+ 「档 × 快照段」逐段。矩阵**单向收紧**：架构定上限，用户可再关小，不能放宽超过上限。「agent 可管理」的整个前提是用户不在场时也安全，双向可调意味着一次误点就让外部档拿到 `taskbar/set-enabled`，而今天零审计、误点没有任何痕迹。逐方法级太细（27+ 方法 × 5 档没人会用，且名单会随受控新增而变）；不提供调节则「单向收紧」变成空话。

## 投影名单

**进投影的既有方法 11 个**（母集 27）：

- 只读 3 — `panel/snapshot`、`desktop/icon`、`taskbar/get-state`
- 布局 5 — `desktop/move`、`desktop/move-batch`、`desktop/pin`、`desktop/unpin`、`desktop/reset-layout`（仅内核 / 后端）
- config 1 — `settings/set-card-opacity`
- 内核插件层 2 — `taskbar/set-enabled`、`taskbar/system-action`（仅内核）

**不进投影的既有方法 16 个**：

- **「面板外的世界」12**（动的是用户文件系统、剪贴板、外部进程，blast radius 超出面板自身）— `desktop/launch`、`desktop/reveal`、`desktop/copy-path`、`desktop/copy-paths`、`desktop/clipboard-copy`、`desktop/clipboard-cut`、`desktop/clipboard-state`、`desktop/trash`、`desktop/rename`、`desktop/paste`、`search/action`、`session/focus`。其中 `desktop/paste` 的剪切语义会移动 / 删除源文件、**无池护栏**、不可逆。
- **纯 UI 态 3**（ADR-0009 已定）— `search/activate`、`search/query`、`search/deactivate`
- **应用生命周期 1** — `app/quit`

**受控新增 21 个能力**（最终方法名与契约形状交《agent 写入插件包的契约与 capability 授予》与《控制面的本地安全边界与凭证》）：

- 插件包 7 — list(R)、read(R，仅内核 / 后端)、install、update、uninstall、rescan、unload（后五走待装载区）
- config·观感与检索 3 — 面板几何、天气经纬度、搜索引擎选择
- config·信任根与持久化 3 — 五工具映射、自启项、护栏配置（均仅内核档）
- 提案 3 — submit、list、approve（仅内核档，且调用方必须是用户交互）
- 回滚点 2 — list、restore（仅内核档）
- 审计 1 — read（仅自己那一档）
- 会话级授权 2 — request（触发确认闸门）、list（自查）

**「面板外的世界」的边界精确化**：一律不进控制面，但**用户插件根不算「面板外」**——它是面板的一等管辖地（投放档这个信任档就是从那儿来的），所以 `plugins/*` 必须经控制面：面板必须知道这次写入发生了（建回滚点、设闸门、记审计），而 `fs.watch` 300ms 后会自动加载，旁路写入根本拦不住。排除「面板外的世界」的理由是：四个后端 agent（kimi / zcode / hermes / dsh）**自己就有文件工具**，经面板中转去删用户桌面文件没有正当需求，反而把面板变成「绕过 agent 自身护栏的一只手」——agent 侧的文件操作有它自己的确认机制（要 `--yolo` 才跳过），而经控制面调 `desktop/trash` 会绕过渲染层那个唯一确认浮层，两边护栏同时失效。

## Considered Options

- **控制面 = `BridgeMethods` 全表的投影，不新增方法** —— 插件包类投出来是空集、config 类只有 2 法，等于把 charting 时明确定到最宽的边界（含插件包增删改与 config 全字段）偷偷收窄。
- **插件包管理走文件系统旁路，控制面只暴露 `plugins/rescan`** —— 这正是现状，而现状的后果已被量化：投放一个目录 ≈ 300ms 后在渲染进程执行任意 JS + 未裁剪全表 27 方法。把「增 / 改」留在那里等于把 RCE 留在闸门之外，也正是 ADR-0009 拆出投放档要防的那条路。
- **档之间不单调，30 个格子各自独立定** —— 表达力最强，但矩阵不可审计（无法断言「外部档能做的后端档一定能做」），且「用户可再关小」没有可操作的语义。
- **宽严顺序按 ADR-0009 的列举（内核 > 投放 > 后端 > 外部）** —— 「面板内比面板外可信」这个直觉被探针推翻：投放档的信任来源是「投放进目录即生效、无发布把关」，实测等于 RCE；外部档至少有「用户手动配置连入」这个显式动作。ADR-0009 拆出投放档的整个理由就是它不可信。
- **内核档与其他档同待遇（也带确认闸门）** —— 用户点一下、面板弹一句「你确定吗」，而确认闸门的目的本是让不知情的人知情；代价是 UX 变差且用户会学会无脑点同意，闸门失效。
- **内核档全免（不建回滚点、不进审计）** —— 丢掉两样与「调用者是否知情」无关的东西：用户也需要后悔药（`desktop/reset-layout` 今天连渲染层确认都没有、一按就没且不可逆），也需要知道刚才哪个内置卡片改了什么（今天零审计）。
- **把内核档再细分成「内核 UI 触发」与「内置插件包触发」两种来源** —— 实施上无处着力：`BridgeService` 今天连 `event.sender` 都不校验（`app/src/main/panel-ipc.ts:48` 的 `_event` 未使用，对比同文件 `:74,79,87` 的 host 三通道各自校验），要区分「哪个渲染帧发起的」得先有身份；且把同一档再细分会让单调性破功。
- **快照拆方法名而非按档裁段（`panel/snapshot` vs `panel/snapshot-lite`）** —— 会让「投影之外是方法不存在」这个护栏变质：同一能力挂两个名字，agent 就会去试另一个。注意仓库里两个先例方向相反——`viewFor()` 支持按接收方裁段，而 `taskbar/status`（`bridge.ts:201-205`，注释明写「与 `panel/changed` 同源同拍，只裁时钟 + 硬件两段」）是拆了独立事件名；选裁段不选拆名的理由是 `taskbar/status` 的消费方是**编译期已知的固定内核窗**，而控制面的接收方是**按档动态的**，拆名会导致「档数 × 段集组合」的方法名爆炸。
- **快照整包给或不给** —— 在 `desktop`（绝对路径 + 用户名）与 `weather`（经纬度）已证实高敏的情况下，等于外部档只能不给，而 in-band 引导语「先调 `panel/snapshot` 了解现状」当场作废。
- **段内字段级裁剪**（如 `desktop` 段给名字不给绝对路径）—— 表达力最强但契约形状爆炸、agent 无法预测自己会拿到什么，且与既有 capability 模型不同构。留作后续票。
- **事件订阅整块交《MCP 传输与宿主进程选型》** —— 会让同一份数据长出两套口径，那正是 ADR-0009 花一整票否掉「两条通路」的理由。本 ADR 决护栏侧（与快照同口径、按档裁段、`search/results` 永不进），传输可行性仍归该票；若它最终判定规范不支持服务端推送（2026-07-28 修订版删了服务端主动请求、改 MRTR），本决策自动降级为「轮询 `panel/snapshot` 的间隔与档位」，不留空洞。
- **`search/results` 也进投影** —— 它的载荷是 Listary **全盘**索引结果（任意文件 path/name/sizeBytes/modifiedAt，不限桌面，`app/src/shared/contract.ts:213-220`），既不属于四类客体、也不是面板自身状态，推给外部 agent 等于送一个全盘文件监视器，敏感度比快照高一个量级。
- **只靠确认闸门，不建回滚点** —— 确认闸门只能防住「agent 明说要干什么」，防不住「写进去的值把文件搞坏」；在零 undo、零备份、且损坏会静默覆写的现状下，这是唯一的兜底。
- **agent 也能触发回滚** —— 见「护栏机制」：会让审计的价值归零。
- **确认闸门超时后降级（降为只读或 dry-run）** —— 降为 dry-run 意味着 agent 拿到了一份它本不该拿到的预演数据。
- **提案批准后由面板自己落地（不记自主管理档、不引用提案 id）** —— 这就是**代发**，形状与 ADR-0009 禁止的那条一字不差（面板解析自主管理的产出、以自己的身份调用控制面），被禁的理由完全适用：借到内核档的完全信任、绕开全部护栏，而闸门装在控制面内、代发不过控制面。
- **提案批准后通知发起的 agent、由它自己再发一次写** —— 最干净，但要求「有一个在跑的 agent」，而自主管理是面板内的持续观察 + 判断，未必有会话可通知。
- **`config` 整列一个开放级，不拆两组** —— 会让「改卡片透明度」和「改信任根」享受同一开放级，而这正是四值开放级要避免的。
- **`plugins.dir` 对内核档保留可写** —— 它不是「一个配置项」而是**投放档信任边界的定义本身**（用户根 = `config.plugins.dir || userData/plugins`，`app/src/main/index.ts:152`）。谁能改它，谁就能把「投放进目录即生效」的那个目录指向自己能用文件工具直接写的地方，之后的投放完全不经控制面——不经待装载区、不经确认闸门、不建回滚点、不进审计。留着这一格等于留着一个「一次受控写换来整条旁路」的口子；内核 UI 今天也没有改它的界面，要改就手改 `app/config.json`，那本来就是开发者动作。
- **护栏配置归入「观感与检索」组（各档可写）** —— 直接自毁：用户关掉的格子，agent 自己打开，单向收紧当场作废。这与 `plugins.dir` 是同一个形状——不是攻破护栏，是改定义护栏的那份数据。
- **护栏配置全档不投影、含内核档（同 `plugins.dir` 待遇）** —— 过严：收紧护栏是个正当动作、需要在设置界面里做，逼到手改文件会让「用户可再关小」实际上没人能用，而单向收紧的全部价值就在这一半。
- **审计只记带闸门的写** —— 太窄：不带闸门的写（如 `settings/set-card-opacity`）单次无害、累积起来能把面板改得面目全非，而正是这类写最需要事后追溯。
- **审计逐次记只读** —— 1Hz 推送下每秒一条，日志瞬间失去可读性。
- **任务栏内核插件层的启停永不对任何 agent 开放** —— 等于偷偷重开 charting 时明确定到最宽的边界；而且它的真风险（托盘黑洞、孤儿窗）已被 Q12 的原子性契约与串行化分别针对，不需要用「一律禁止」来兜。

## Consequences

- **本 ADR 修订 ADR-0009 的两处口径**：`:27`「投影 = 四类客体的读写方法 + `panel/snapshot`」被「以投影为主 + 受控新增」取代（四类客体里插件包类 0 法、config 类 2 法，纯投影到不了边界）；`:28`「事件订阅整块未决」的护栏侧已由本 ADR 决完，只剩传输可行性归《MCP 传输与宿主进程选型》。`:15` 把 `taskbar/set-enabled` 举为「投影之外」的例子，与同文 `:27` 自相矛盾、现又与本 ADR 冲突——那句话是历史记录不重写，另加编注指明举例已失效。**事实性引用错误直接改 ADR-0009 正文**（方法数 25 → 27、内置插件根的运行时路径是 `dist/renderer/cards` 而非源码路径 `app/src/renderer/cards`，`app/src/main/index.ts:30`），地图 #66 的 Notes 同步改。
- **护栏是协作性的，不是强制性的。** 矩阵与闸门只约束「经控制面发起的写」；而外部与后端 agent **都持有自己的文件工具**，能直接写 `userData/layout.json`、`app/config.json`、用户插件根、甚至审计日志本身——绕过全部门禁。排除「面板外的世界」（Q4）决定的是「控制面不提供文件操作」，不是「agent 动不了文件」。这不推翻矩阵（控制面仍是**唯一**能被审计、能有闸门、能有回滚点的路径），但划定了它的效力范围，且**这个边界本身归《控制面的本地安全边界与凭证》**。
- **串行化改变了写方法的返回语义**：`taskbar/set-enabled` 今天是同步翻位 + `persist()` + emit，窗口的建 / 销是事件驱动的异步副作用（`feat/taskbar-takeover` 的 `app/src/main/taskbar/window.ts:281-284`）。「在途」的边界不在 `BridgeService` 里、在窗口控制器里，所以控制面要串行化就必须等控制器的完成信号——即写方法要返回「**副作用已落地**」而非「**状态已翻转**」。这会影响《MCP 传输与宿主进程选型》的超时设计。
- **待装载区改变了 `fs.watch` 的既有语义**：经控制面写入的包**不是**投放即生效。用户手动投放的路径不变。《agent 写入插件包的契约与 capability 授予》需要在这条约束下设计契约，并接手 capability 的**档级上限**机制（用什么形状表达「manifest 只能在所属档的段集上限内声明」由它决）。另需注意插件 id 冲突是**先到先得、用户插件顶不掉内置**（`app/src/main/plugins/service.ts:206-211`）。
- **自主管理那一行是「形状不同」而非「更窄」**：它对全部六列都不能直接写，只走提案通道。《自主管理的接口预留与数据口径》要接手的约束是：永不宽于后端档、只能提案、提案带过期、批准即一次性授权、落地必须记自主管理档并引用提案 id、读数据也必须经控制面（否则审计有洞，且它会变成另一条「不过控制面」的路径，正是 ADR-0009 封死的那种）。遥测口径也受本 ADR 约束：审计已覆盖读写，提案队列本身是新的数据源。
- **票面「任务栏内核插件层的启停是否永不对自主管理开放、只允许用户显式发起」的答案**：永不**直接**开放，但可以提案；而 `proposals/approve` 只能由内核档的用户交互触发，所以「只允许用户显式发起」这个要求被提案机制本身满足了，不需要额外一条禁令。
- **两处既有缺陷不在本 ADR 的射程内，但被它照出**，需单独立票：① `w.once('closed')` 无身份校验导致的孤儿置顶条带（九个 taskbar 分支一处都没修，目标形态下还会连带误注销新窗的 AppBar 占位）；② `app/src/main/taskbar/native.ts:23-25` 的 `nativeTrayWnd()` 是裸 `FindWindowW('Shell_TrayWnd')`、**不按属主 PID 过滤**（对比 `app/accept/tray-spike.js:146-151` 的 `realTrayHwnd()` 专门用 explorer PID 过滤，说明碰撞是已知的），而托盘宿主注册了同名窗口类且实测赢下竞争（48 号证据 `tray-competition win:true` 3/3）——推测工单56 之后 `hideNativeTaskbar()` 命中的是宿主自己的 0×0 隐藏窗，导致 explorer 真任务栏根本没被隐藏、条带按 `clearance=0` 落到屏底与它同矩形重叠。**此组合从未真机验证**：`app/accept/` 无 56/57 电池脚本、evidence 无 `56-*`/`57-*` 文件、`49-`/`55-` 事件流里 `tray-host-ready` 计数为 0。
- **本 ADR 只定护栏的分级与机制**。凭证怎么铸、存哪、怎么轮换、面板重启后怎么办，归《控制面的本地安全边界与凭证》；新增方法的契约形状与 capability 表达归《agent 写入插件包的契约与 capability 授予》；传输与宿主归《MCP 传输与宿主进程选型》。提案队列的呈现形态（用户在哪儿看提案、怎么批）是 UI 实施，不在本地图范围。
