# 收编广播的溢出层副作用按「文档化接受」收口（广播保留，降噪不取）

背景：TrayHost 每次启动广播 `TaskbarCreated`——它是**收编的唯一入口**（通知区域的图标来源：响应广播的托盘应用把图标改注册进本面板竞争窗）。工单142 起因：#119 取证实证每次广播会让未提升的响应应用在系统**溢出层**留下条目（Wallpaper Engine ×18，2026-10-11 晨），且条目不随响应应用退出消失（生产退出硬杀子进程无任何广播）——看上去是系统层单向累积的副作用，直到 explorer 重启或用户手清。

## 新证据（2026-10-11 并案取证，工单142+#103，docs/audit/2026-10-11-t142-103-joint-forensics.md）

堆积**自限，不单向**：

- 同日多轮面板启停后，溢出层 WE 基数已从 ×18 自然衰减到 ×9；
- 定向实验（3 轮重启，每轮停＝交还广播、起＝收编广播）把溢出层 **67 项清到 0**——广播链本身就是 explorer 重建溢出层的触发器，堆积在正常使用（面板反复启停、验收轮反复拉起）中被持续清理。

## 决策：(a) 文档化接受

保留广播不动；把副作用与自限性登记为收编机制的已知性质（本 ADR + 词汇表「收编」注记 + 审计报告）。

**备选否决**：

- **(b) 减少广播次数**——广播是收编的唯一入口，任何「少播」都直接砍图标来源；为抑制一个自限的副作用去冒断入口的风险，方向反了。
- **(c) 退出侧补交还广播**——原以为退出对称能清堆积，实测恰恰相反地理解了机制：交还广播与收编广播同属广播链，**链本身即清理机制**；生产退出补广播等于为「已被自然清理的东西」引入一次全应用重注册 churn（票面自警过可能加剧），得不偿失。且强杀路径（crash/任务管理器）根本走不到退出钩子，对称广播覆盖不了主场景。

## Consequences

- 不改任何代码；副作用知识沉淀在词汇表与审计链。
- 后续若出现**速率性**证据（堆积影响 explorer 启动/内存/交互延迟，而非仅条目计数），凭新证据重开决策。
- #103 缺陷②的修复（nativeTrayWnd 属主过滤）与本决策正交：那是查错窗的问题，不是广播的问题——修复另排（spec #145）。
