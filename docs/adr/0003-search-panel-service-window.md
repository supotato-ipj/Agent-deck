# 搜索面板是数据服务自有的常驻窗口，而非壁纸层或独立应用

需求是把 Listary 搜索框「嵌进」壁纸并在桌面上直接点选、打字。但 ADR-0001 已确立壁纸网页层在桌面上收不到点击、也拿不到键盘焦点；Wallpaper Engine 官方唯一的网页键盘输入通道要求「URL 加载 + 隐藏桌面图标」，会摧毁建立在可见图标之上的整个桌面分区体系。因此「点框打字」的承载面只能是数据服务自己创建的原生窗口：待机时以 DECK 同款视觉伪装成壁纸的一部分，点击激活、失焦退回待机；检索经 Listary 7 本地 HTTP API 完成（该 API 无 CORS，恰好因为调用方是服务而非浏览器而不受影响）。壁纸网页层保持 GET-only、不新增写端点、不新增常驻进程——搜索面板的窗口线程寄生在数据服务内，与其共存亡。

## Considered Options

- **壁纸网页层直接承载输入** — 平台硬限制（键盘与点击均不可达），不可行，非取舍。
- **改用 URL 加载壁纸 + 隐藏桌面图标换取网页键盘输入** — 为一个功能摧毁桌面分区体系，明确否决。
- **独立小进程承载搜索窗** — 需要多养一个常驻进程，与「能力全放数据服务、与壁纸共存亡」的部署决策相悖（ADR-0001 同款理由）。
- **底层鼠标钩子监听点击区域 + 真瞬态窗口** — 为措辞上的「瞬态」引入全局鼠标钩子，侵入性强且更脆，否决。
- **数据服务常驻待机窗（选定）** — 唯一同时保住「点框打字」「图标分区体系」「单一常驻进程」三个约束的解。

## Consequences

- 数据服务从无头服务变为带一个 UI 窗口；窗口线程须与主服务线程隔离，窗口异常不得拖垮数据服务。
- 待机视觉与壁纸按物理像素对齐，非 100% 缩放会出现偏差（与分区标签同款已接受限制）。
- 搜索链路完全不经壁纸网页层，不引入 HTTP 写端点，ADR-0001 的 GET-only 附带收益保持完整。
- 依赖 Listary 7 本地 HTTP API（beta、仅监听 127.0.0.1、只读、无 CORS、无 keep-alive）；引擎不可达时面板须呈现引擎离线态而非失败。
- 查询词不写入自建使用日志（对齐 ADR-0002 的隐私边界）；Listary 自身 SearchHistory 照常记录，属其原生行为。
