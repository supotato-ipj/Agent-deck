# Spec: TERMINAL 02 壁纸显示 Qoder 任务状态

Status: ready-for-agent

## Problem Statement

用户在电脑上通过 Wallpaper Engine 使用「TERMINAL 02」动态壁纸，壁纸能显示时钟、天气、系统性能等自定义信息。用户日常同时运行多个 Qoder AI 编码会话，但这些会话的任务进展只存在于各自的 IDE 窗口里——用户无法在桌面背景上一眼看到"agent 是否还在跑、任务进行到第几步、当前在做什么"，需要频繁切换窗口查看。此外，壁纸原有的性能监控区块因配套服务端从未运行而一直空置。

## Solution

自建一个本地 HTTP 数据服务，替代壁纸原本配套（但未运行）的 PerformanceMonitor 服务端：它一方面采集硬件指标（CPU、内存、GPU、网速），另一方面扫描 Qoder 落盘的会话与任务文件，汇总出"最近活跃会话"的运行状态。壁纸端复用其内置的每秒轮询管线获取数据，并通过用户级布局覆盖脚本在屏幕右栏中下部（天气信息之下、滚动日志之上）渲染一个 QODER 状态区块 + 精简版硬件区块。

## User Stories

1. 作为桌面用户，我想在壁纸右栏中下部看到 QODER 区块，以便不切换窗口就能掌握 AI 会话动态。
2. 作为桌面用户，我想看到最近活跃会话的 RUNNING/IDLE 状态灯（RUNNING 高亮闪烁），以便一眼判断 agent 是否还在干活。
3. 作为桌面用户，我想看到活跃会话总数角标（如 SESSIONS 003），以便知道除主显示会话外还有其他会话在运行。
4. 作为桌面用户，我想看到当前会话的项目名（工作目录末段），以便确认状态属于哪个项目。
5. 作为桌面用户，我想看到任务进度（已完成数/总数 + 文本进度条），以便估计工作还剩多少。
6. 作为桌面用户，我想看到当前 in_progress 任务的标题（中文原样显示、按约 16 个全角字符截断），以便知道 agent 此刻在做什么。
7. 作为桌面用户，当没有任何活跃 Qoder 会话时，我想看到明确的待机态（如 QODER OFFLINE），以便区分"没会话"和"服务挂了"。
8. 作为桌面用户，我想在同一区块附近看到精简硬件指标（CPU、RAM、GPU+VRAM、NET 上下行共 4 行），以便顺带掌握系统负载。
9. 作为桌面用户，我想让 GPU 数据来自 nvidia-smi（已验证可用），以便在 psutil 无法提供 GPU 指标的 Windows 环境下仍有真实数据。
10. 作为桌面用户，我想通过手动命令启动数据服务，以便先验证效果，之后再决定是否配置开机自启。
11. 作为桌面用户，当数据服务未启动或崩溃时，我想让壁纸其余部分（时钟、天气、日志）不受影响，以便桌面始终可用。
12. 作为桌面用户，当 Qoder 升级导致其文件格式变化时，我想让服务端容错降级（解析失败返回空状态而非报错崩溃），以便壁纸不显示错误数据。
13. 作为壁纸维护者，我想在改动 Workshop 目录前留有全量备份和一键重打补丁脚本，以便创意工坊更新覆盖后能快速恢复改造。
14. 作为壁纸维护者，我想把 Qoder 渲染逻辑放在用户级布局覆盖文件中，以便与壁纸原版布局解耦、升级不易丢失。
15. 作为桌面用户，我想让左栏在性能区块移走后自动重排（接受间距变化），以便先看实际效果再决定是否补占位。

## Implementation Decisions

- **架构路线**：复用壁纸内置的性能监控轮询管线（每秒 fetch 本地 HTTP 服务），不新建独立区块。原左栏的性能显示容器移动到右栏 `.bottom`，插入位置在天气/鼠标信息区块之后、滚动日志区块之前。
- **服务端**：单文件 Python 脚本（标准库 HTTP server + psutil），存放于研究工作目录，监听 `127.0.0.1:5000`（沿用壁纸属性默认端口，不改壁纸配置）。手动启动，暂不配置自启。
- **API 契约**：`GET /performance` 返回 JSON：
  - `psutil` 对象：`cpu`（%）、`memory`（%）、`memory_gb`（"used/total" 字符串）、`gpu_usage`（%）、`gpu_temp`（°C）、`vram_usage`（%）、`download_speed` / `upload_speed`（KB/s）。GPU 三项由 nvidia-smi 查询获得；CPU 温度不提供（Windows 下 psutil 拿不到，原版依赖 HWiNFO）。
  - `qoder` 对象：`active_sessions`（整数，活跃会话总数）与 `session`（最近活跃会话：项目名、running 布尔、tasks_done、tasks_total、current_task 文本）。
- **Qoder 数据源**：会话活跃度按各项目目录下会话 JSONL 文件的修改时间判定（90 秒内有写入 = 活跃 = RUNNING，否则 IDLE）；任务清单读取会话对应任务目录下的每任务 JSON（字段含 subject/status/blocks/blockedBy）；"当前任务"取 status 为 in_progress 的任务 subject。会话与任务的关联键为 sessionId。
- **会话选择**：多个活跃会话时只展示最近写入的一个，另以角标显示活跃总数。
- **壁纸端改动**：
  - 主 HTML 文件：移动性能容器 div；在轮询函数中把响应里的 `qoder` 字段透传给布局构建函数（约 2 行改动）。
  - 新建用户级布局覆盖文件（壁纸原生支持该覆盖机制，优先于默认布局加载）：渲染精简硬件 4 行（CPU / RAM / GPU+VRAM / NET DL+UP，不含磁盘行）+ 空行 + QODER 区块约 5 行。
- **样式**：RUNNING 状态复用壁纸现有 `data-indicator` 高亮类；中文 subject 依赖 CEF 字体回退渲染，按显示宽度截断（约 16 全角字符）；无活跃会话时显示待机文案。
- **容错**：服务端所有文件扫描与解析包裹异常处理，失败时返回 `qoder: {active_sessions: 0, session: null}`；壁纸端 fetch 失败走既有错误日志路径，不影响其他区块。
- **可恢复性**：改动前对壁纸目录做全量备份，并提供一键重打补丁脚本，均存放于研究工作目录。

## Testing Decisions

- **唯一测试接缝**：HTTP 接口 `GET /performance` 的 JSON 响应。服务端全部逻辑（psutil 采集、nvidia-smi 调用、Qoder 文件扫描、容错降级）都验证其对这一外部契约的输出，不测内部实现细节。
- 好的测试 = 用 curl/脚本断言响应结构与字段语义：有活跃会话时 `session` 非空且进度数字与磁盘上任务文件一致；无活跃会话时返回待机结构；Qoder 目录缺失/损坏时仍返回 200 与空状态。
- **渲染验证**：用浏览器直接打开壁纸主 HTML 文件（本地服务运行中），截图检查右栏 QODER 区块位置、中文回退渲染、RUNNING 高亮、左栏重排效果。无自动化 UI 测试先例，以人工目测 + 用户在 Wallpaper Engine 中最终验收为准。

## Out of Scope

- 开机自启/服务化（验证满意后另行处理）。
- 在 Wallpaper Engine 编辑器中另存为本地项目（作为日后加固手段，不在本次实施内）。
- 显示多个会话的逐会话明细（仅角标计数）。
- CPU 温度、磁盘占用、HWiNFO 数据源。
- 会话历史、token 用量、模型名称等 JSONL 中可挖的更深指标。
- 对 Qoder 写入行为的任何干预（纯只读）。

## Further Notes

- 已验证环境事实：Python 3.14 + psutil 7.2.2 可用；nvidia-smi 可返回 GPU 利用率/温度/显存；5000 端口当前无占用；壁纸为 web 类型（HTML/JS），其 CEF 环境允许 fetch localhost（天气功能已在用）。
- 风险：Workshop 目录可能被创意工坊更新覆盖（备份+补丁脚本缓解）；Qoder 文件格式（当前版本 1.1.49）非公开 API，升级可能变化（容错降级缓解）。
- 长工具调用期间（如数分钟的命令执行）会话文件无写入，可能被误判为 IDLE；90 秒阈值下影响有限，接受该误差。
