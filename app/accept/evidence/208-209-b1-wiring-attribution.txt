五、行为变更申报（四条判别面差异，PR 描述单列）

① **寻窗判据多一道「可见性」**
   - 改前：正典 `waitPanelWindow` 按 pid ＋ `Chrome_WidgetWin_1` ＋ 标题 `AGENT DECK` 三重甄别，
     **不含可见性判据**。
   - 改后：句柄 `findWindowByTitle` 追加 `isWindowVisible(h)`（工单206 审计必改项）。
   - 影响：面板本体窗正常可见 → 行为上无差；面板被隐藏时改判「就绪窗未现」（更严）。
2. **句柄 boot 解析多一道 `pid > 0` 过滤（裁决 15 接受）**
   - 改前：正典 `readEvents().filter((e) => e.type === 'boot' && e.t >= sinceMs).pop()` **不要求 pid > 0**。
   - 改后：句柄 `latestBoot` 追加 `&& Number(e.pid) > 0` → 一条 pid 缺失/为 0 的 boot 会被跳过。
   - 影响：面板 boot 恒带 pid（随后就取 `boot.pid` 寻窗）→ 多半是空转差异；**更严更安全**。
3. **四处用句柄缺省 since 门（裁决 14 ＋ 一处形态偏离）**
   - `#1 P1 首启`：事件文件在电池启动时已被 `unlinkSync` 清空 → 文件里只剩新面板的 boot →
     「since=0」与「since=发射时点」接到的是**同一条** boot。
   - `#10 P6 改几何`：**上一步先物理 `unlink` 了事件文件**（该步保留未动）→ 旧 boot 已被清空，
     「无门」与「since=发射时点」同形；这是「无门也安全」的唯一依据，删文件那一步必须保留。
   - `#12 P10E 退出面板按钮`：`t0e` 早于发射时点，而 boot 存证的 `t` 必然晚于发射时点
     （面板是发射后才起、才落 boot）→ 两门接到的是**同一条** boot。
   - `#3 P5-ICON2`（**本刀相对对照表的一处形态偏离，见 §六①**）：现行流程里**没有** `stopPanel()`
     ——面板是被定点 `taskkill /PID panelPid /F` 清掉的（外层守卫要活着还原原生图标）。
     对照表 §3 把该点列为 `relaunch({ sinceMs })`，但句柄的 `relaunch` 会**整树强杀**（`/T`）
     把外层守卫一起带走 → 守卫不还原图标 → `icons-restored` 存证不到 → **本段判死**。
     故本刀在该点**只发射不重退**（`handle.launch` ＋ `handle.waitWindow`），since 门用句柄缺省：
     原 `relaunchT0` 就取在发射前那一瞬，与缺省门（发射时点）可证等价。
4. **1684 不迁（裁决 12）**
   - `battery.js` 的 P5-ICON2 守卫退出判定仍用电池侧 `isAlive(child.pid)`——`child` 是电池拉起的
     **发射子进程**，而句柄 `alive()` 优先查**面板自报 pid**；两者在 Electron 父子进程下可能不是
     同一进程 → 改用 `handle.alive()` 是 pid 口径变更（行为变更），本刀不迁。
   - 本行**不在 #209 范围内**，登记备查。
