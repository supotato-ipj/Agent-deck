三、地雷 1（issue #217）——dgc 的 for(;;) 多读一次：实测结果
═══════════════════════════════════════════════════════════════════════

  口径：dgc 正典 waitEvent 是 for(;;) 形态（读 → 判 deadline → 睡 60ms），比磁带的
  while (Date.now() < deadline) 口径**多读一次** → 落在最后 60ms 窗口内到达的事件，
  dgc 接得到、磁带接不到 → 绿段可能变红段。

  处置（#217 口径，照办）：磁带是「一份正典」（while 是 7 块里 6 块的形态）→ **磁带不改**；
  批3 落地必须**实测 dgc 全轮**，红了即回归（不接受「概率性」解释）。

  实测：**两轮全绿**（轮1、轮2 均 PASS 47/0/0），段级三元组与基线逐段相同，零红段、零 EXENV。
        → 该 60ms 窗口在本刀**未落地为红段**。

  裕度核对（逐点）：dgc 的 18 个 waitEvent 超时档全为 ≥3000ms
    （3000×2：menu-opened(cardId 谓词) 与 multi-toggled；4000×9；6000×3；8000×2；10000×1；20000×1）。
    单点命中该窗口的概率上界 ＝ 60/3000 ＝ 2%；且只有「事件恰好在超时前最后 60ms 才到」
    时才咬——那种情形本身已近失败线。实测两轮 0 红。

  结论：**不记 issue**（红了才记；实测未红）。磁带口径不动，`while` 保持正典形态。

四、boot 选取口径变更（首个 → 最后一个）：本刀两块的惰性论证
═══════════════════════════════════════════════════════════════════════

  变更来源：句柄 waitWindow 内部按缺省门取本代次**最后一个** boot（编排台账 §8 裁决 4）。
  dgc 与 tray-spike 的现行 waitEvent('boot', …) 取**首个**。本票未申报即成立 → PR 描述单列一节。

  惰性论证（逐块）：
  - 166-doc-group-cards：startPanel 每次发射前**物理截断**事件档
    （`fs.writeFileSync(EVENTS_FILE, '', 'utf8')`），且截断发生在 `handle.launch()` **之前**、
    旧面板已被强退 → 每次代次的档里只有本代次那一条 boot
    → 句柄缺省门（＝本次发射时点）下 **首个 ≡ 末个** → 本电池上该变更**惰性**（可证等价）。
  - 48-tray-spike：句柄六方法面里**只有 waitWindow 会查 boot**（latestBoot）；
    tray-spike 全程**不调** waitWindow（自己在 P3b 用 `tape.latest('boot')` 取面板 pid 寻窗）
    → 句柄侧根本不做 boot 查找 → 本电池上该变更**惰性**。

  方向：变更方向**更安全**（句柄缺省门＝本次发射时点，结构性堵死旧 boot 混入）。
  处置：申报而不回退（裁决 4 明写「取最后一个是承重的，不可改回首个」）。

五、两处「无验证 killTree → 验证强退」的处置与时序风险核对
═══════════════════════════════════════════════════════════════════════

  母票 #202 决策 8 授权（批2 已覆盖 taskbar 族五块那几处；**全仓共 7 处，本票这 2 处**）：
    ① 166-doc-group-cards 的 killPanel（内联 taskkill /PID panelPid /T /F ＋ child.kill()，不验消失）
    ② 48-tray-spike 的内联 taskkill（child.kill() ＋ sleep(600) ＋ taskkill /T /F，不验消失）
  两者同刀升级为 `handle.stop()`（工单112 的强退序列：优雅终止 → 整树强杀 → 有界等待并**验证消失**）。

  时序风险核对：
  ① 清场变慢上限：单次 stop() 最坏 ＝ 800ms 宽限 ＋ 5000ms 验证窗 ≈ **5.8s**（原：dgc 毫秒级、
     tray-spike ≈600ms）。本轮 dgc 3 次（两处段内定点杀 ＋ 轮末清场）、tray-spike 1 次，
     **实测全部 gone=true 秒退**，未触发变慢；段账目耗时反降（见 §二）。
  ② restart-clear-required 中止路径（gone=false 时）：
     - dgc 段内两处定点杀（stopPanelOrAbort）→ rep.exclude(归因 panel-forcekill) ＋ throw 中止后续段
       （由电池 try/catch 汇流，不吞）；**轮末清场只入账不中止**——清场抛错会拦住 finish()
       → 控制器不退 → 验收槽租约挂死。
     - tray-spike P6 → rep.exclude ＋ throw 中止后续段（P6 是末段，中止不吞尾段）。
  ③ **进程树口径的差异（如实申报）**：原实现**总是**先做 taskkill /T /F 整树硬杀；句柄序列**先**
     优雅终止（child.kill），只有宽限窗内仍存活才升级到整树强杀。故 child.kill() 成功
     （浏览器主进程已死）时，句柄**不再**下发 /T 整树强杀——Electron 的渲染/GPU 子进程靠
     「浏览器主进程已死 → IPC 通道断 → 自行退出」收敛，不再有 taskkill /T 兜底。
     - 实测核销：三轮跑完查进程表，**无残留 electron 进程**（只剩 msedgewebview2 的
       SearchHost/TickTick，与本仓无关）。
     - 受影响判据面（逐条核）：dgc 依赖面板**窗口**消失（浏览器主进程 → 窗随之消失）与
       CDP 端口释放（浏览器主进程持有 → 随之释放）；tray-spike P6「交还真托盘」判的是
       **explorer 的** Shell_TrayWnd（按属主 pid 过滤），我方竞争窗在浏览器主进程 → 随进程消失。
       实测三轮 P6 全绿。
  ④ 证据档 fd（裁决 10 第②条）：句柄的 archive 形态**不 close** fd；dgc 注入 openArchive 记账、
     轮末 close（本轮 3 只 fd：三次起面板各开一只）。这是**资源卫生**项，不涉断言面。
