## 3. 机制核销清单（本刀引入的每一处可能机理，逐条排除）

| 候选机理 | 核销方法 | 结论 |
|---|---|---|
| 磁带节：8 处「事件已取回后的 JS 侧新鲜度门」迁 `since`（49 的 1093/1104/1152/1163/1178/1827/1853/1897） | 等价性证明依赖「事件流 t 在文件序上单调」⇒ 实测基线轮事件档 1071 条、**t 非单调 0 条**、88 帧 taskbar-geometry 非单调 0 条 ⇒ `max{t}` 与 `max{t ≥ gate}` 在门成立时同拍、门不成立时同为「无候选」 | **排除**（等价成立） |
| 句柄节：`waitWindow` 改按**最后一个** boot 寻窗（boot 选取口径变更） | 本轮事件档 8 条 boot 存证、**8 次发射对应 8 条 boot、pid 互异、t 严格递增** ⇒ 「首个 vs 最后一个」在每段发射窗内是同一条 | **排除**（口径变更在本电池惰性） |
| 句柄节：验证强退**跳过整树强杀**（优雅终止即死 → `isAlive` 假 → 不强杀）致渲染/GPU 残留 | 轮后即刻查进程：**无残留 electron 进程**；且显式 `taskkill /PID panelPid /T /F` 仍在序列内 | **排除** |
| 句柄节：优雅终止改变了面板退出路径（`before-quit` 还原钩子在旧路径不跑、新路径跑） | Windows 上 `child.kill()`＝`TerminateProcess`，**不产生 `before-quit`**；旧路径 `taskkill /F` 同样不跑 ⇒ 两侧钩子行为一致 | **排除** |
| 句柄节：`waitWindow` 轮询间隔 120ms→200ms 造成段内时序漂移 | 段起点漂移实测：P8 +0.5s / P9 +0.9s / P13 +2.4s / P20 **+7.0s**（整轮 156.6s→163.6s，+4.5%，仍在 240s 预算内）；P15B 的臂预算 6s/10s 未被吃掉 | **排除**（量级远小于臂预算） |
| P6 红 | P6 段内**无任何本刀改动的调用点**（无磁带调用、无句柄调用；只有 `cdpEval` ＋ `findWindow` 逐字未动） | **排除**（与本刀无关的既有竞态） |

## 4. 验证强退升级的时序风险点核对（工单211 明列）

| 风险点 | 实测/核对结果 |
|---|---|
| 副电池清场变慢（优雅宽限 800ms ＋ 验证轮询 ≤5s） | 实测整轮漂移 **+7.0s/163.6s（+4.5%）**，段预算与臂预算均未受影响；P8/P9/P10(b)/P12(b)/P17/P20 各次重拉均照旧到位（见 §2 段级对照） |

## 5. 随附的 PR 描述申报正文（编排者可直接取用）

### 5.1 唯一有意行为变更：无验证 killTree → 验证强退（#202 决策 8 授权）

- **变更面**：taskbar 族五块共 14 处清场点（49 的 8 处、50 的 2 处、51 的 1 处、55 的 1 处、156 的 1 处
  ＋ 50 的 A4）由「`taskkill /T /F` 发完就走、不验消失」升级为句柄 `handle.stop()`：
  **优雅终止 → 整树强杀 → 有界等待并验证消失**。
- **理由**：原实现把「面板已死」当既定事实放行重启；停摆面板残留会撞单实例守卫，
  新面板被拒收 ⇒ 后续段成片失真（工单112 级联机理对副电池同样成立）。
  升级后 `gone=false`（`outcome='restart-clear-required'`）＝**中止信号**：段内清场入环境降责账
  （`rep.exclude`，归因 `panel-forcekill`）并 throw 中止后续段；收尾清场**只入账不中止**
  （清场段抛错会拦住 `finish()` → 控制器不退 → 验收槽租约挂死）。
- **时序风险与核对**：清场变慢实测 +7.0s/整轮（+4.5%），段/臂预算未受影响（§4）；
  五块五轮 ＋ 50 两轮均未触发 `restart-clear-required`。
- **一处刻意不迁**：`50-taskbar-carry` 的 A3 崩溃路径保留**定点** `killTree(panelPid)`
  ——该段的段前提就是「面板整树死、**守卫存活**」（守卫以 `panel-exit` 还原原生任务栏）；
  句柄 `stop()` 会连带终结发射子进程（＝守卫载体）⇒ 段前提不成立。其「验证消失」由 A3 既有
  `waitExit(child, 15000)` 承担（守卫随面板死亡而退＝面板已死的证据）。

### 5.2 未申报的行为变更：boot 选取口径（首个 → 最后一个）

- **变更面**：五块共 18 处 `waitEvent('boot', …)`（正典 `.find()` ＝ 首个）迁到句柄后，
  寻窗用的 boot 改为**本代次最后一个**（裁决 4 现行口径；句柄缺省门＝发射时点）。
- **方向更安全**：句柄的 since 门＝本次发射时点，**结构性堵死旧 boot 混入**；这些调用点多数
  根本没有 since 门，旧 boot 混入的老坑本就存在。
- **本批实测惰性**：49 电池一轮 8 次发射对应 8 条 boot 存证、pid 互异、t 严格递增
  ⇒ 每段发射窗内「首个」与「最后一个」是同一条 ⇒ 本批**无行为差**；但口径变更仍按章法申报。
- **boot 存证等待仍在磁带侧**（面板自报 pid 由此取得）——句柄六方法面不暴露面板自报 pid
  （同裁决 12 的口径）；句柄内部按其缺省门自行解析 boot 寻窗。

## 6. 遗留

1. **`restart-clear-required` 中止路径未被实跑覆盖**（五块五轮均未触发）。该路径的时序正确性
   目前只有单测与主电池先例背书；若需真机覆盖，须人为制造「强杀后仍存活」（如挂起进程），
   超出本批范围。
2. **49-taskbar 在本机是红-prone 面**（基线亦红、红段逐轮移动）。合并门若要求 49 的绿轮，
   需在**无人值守的安静窗口**重跑（基线 B1 与本刀 R3 都在同机拿到过 42/0）。
3. **P6「原生还原=false」是既有竞态**（条带销毁 → 面板还原原生任务栏 → 电池随即查视图事实），
   与本刀无关，但会污染 49 的合并门读数；建议另开 issue 记「P6 应等还原存证而非查视图事实」。
4. **P19 的 `EXENV`（机器态：桌面滞留项 exe 富化空串）与基线逐字相同**，是既知环境账，非本刀引入。
